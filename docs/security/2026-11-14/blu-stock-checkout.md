# Blu checkout with pre-funded stock

The opt-in checkout allocates an invoice and reserves one internal stock unit atomically. The existing available-unit query now serves both transactional reservation and legacy fulfillment. The owner receives the saved destination and exact amount. Reserved credentials stay private until payment approval. One unpaid order per buyer can hold one unit.

The bounded timer releases unpaid reservations after invoice expiry. Receipt review has a 24-hour grace period and matched bank observations keep their stock held for operator decision. Receipt uploads require a valid numeric tracking or reference value for these orders. Absent or malformed references fail before consuming a receipt slot. Legacy receipts keep their previous validation.

Signed Blu evidence continues to match by destination, amount, bank time and receipt identifier. The worker can select customer stock receipts when enabled. Admin approval requires an unambiguous match for that exact receipt, then delivers and approves in one transaction. Only enum-valued bank evidence appears in the receipt queue DTO. Mock checkout and historical mock callbacks cannot claim stock in production with the mode enabled. The collector treats a signed duplicate identity conflict as a review result.

The disposable suite proved concurrent final-unit orders, immutable card, owner isolation, stock recovery, preservation of matched holds, denial of a normal buyer's approval, denial of manual approval before a bank match, exact signed evidence and a single successful approval with one delivered credential. The matched-hold regression reproduced the release of one unit before the fix. A receipt-approval regression reproduced approval without evidence before that check was added. Full verify, lint, local production build and Docker builds passed. Both dependency audits reported zero findings.

Release `20261114-blu-stock-checkout` is deployed with `BLU_STOCK_CHECKOUT_ENABLED=false`. API/database health, admin receipts route, active timer, Nginx validation and public preview HTTP checks passed. A pre-release database archive and prior API/web images were retained. No live payments or supplier purchases were executed during this implementation.

The ready-to-ship flow still needs genuine available stock, a live payment rollout and a complete customer-order trace on the configured card. The Blu bank feed does not establish independent final settlement, so administrator approval remains part of the flow. Each base invoice price has a bounded pool of 249 distinct discounts. Reusing bank amounts safely and scaling the collector beyond its current bounded workload require separate validation before high-volume use. The supplier-funded customer checkout is still disabled. Its purchase APIs do not enforce the displayed maximum charge.
