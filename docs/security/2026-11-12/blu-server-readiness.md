# Blu server readiness

The reverse tunnel on the Iran server runs under `oosta-blu-tunnel.service`, enabled at startup with automatic restart. A controlled stop of its SSH process changed the PID from 54731 to 55043 and systemd reported one restart. A fresh key-authenticated login through the pinned host key then worked. The storefront listener was verified on loopback only, at `127.0.0.1:42292`.

The Iran host verified TLS and HTTP/2 against the Blu gateway and ran the pinned upstream protocol key exchange successfully with Node 24.22.3. The runtime was downloaded from nodejs.org and checked against the distribution SHA-256 manifest. The upstream checkout is at commit fa159bc53a8432f922b7c57572e3db9669e29520. No upstream web server or npm dependency was installed for the probe. The probe runs as a separate unprivileged account in a transient systemd unit with restricted filesystem access, no core dumps and a time limit. It disables upstream session load/save in memory, rejects noninteractive enrollment, and prints only a sanitized result and a transaction count. The probe does not retain a reusable device session. No session file was present after the connectivity check.

The account owner can run the probe from a private terminal using:

```sh
systemd-run --quiet --pty --wait --collect -p User=oosta-blu-probe -p NoNewPrivileges=yes -p ProtectSystem=strict -p ProtectHome=yes -p PrivateTmp=yes -p LimitCORE=0 -p RuntimeMaxSec=300 /opt/oosta-blu/node/bin/node /opt/oosta-blu/shadow-check.cjs
```

Local verify, lint, production build and both dependency audits passed. The bank key exchange and noninteractive denial were exercised on the Iran server. The account owner ran the private probe and reported `BLU_HISTORY_READ_OK rows=5`. That probe alone does not establish authoritative credit, account binding or settlement fields. Order matching, unique amounts, payment confirmation and automatic delivery are not active. The separate `--deposit` probe checks an existing incoming transfer without moving money or updating the store. It scopes the read to one receiving account and its 20 latest transactions, compares raw receiving IBAN, credit direction, integer IRR amount and timestamp shape, and requests detail for up to five candidates to compare the receiving bank's receipt code. It prints only a fixed result. The syntax check and two synthetic checks passed on Windows and the Iran server. The live match and bank finality remain unverified. No live bank data is included in the test fixtures.

The owner reported `BLU_DEPOSIT_NO_MATCH` for the first real receipt probe. The previous result merged distinct failure paths. A diagnostic revision reports only aggregate counts for decoded credits, exact amount, bank IBAN presence and equality, timestamp shape, candidate IDs, detail records and receipt-code matches. The matching criteria and bounded history/detail reads are preserved. Synthetic regression failed before the diagnostic function existed, then passed locally and on the Iran host. The actual cause awaits the new sanitized result. This does not change any order or payment state.

## Persistent device enrollment

The owner explicitly approved retaining the Blu password encrypted on the Iran host for unattended renewal. `oosta-blu enroll` runs the owner prompts in a private TTY, validates the session by reading a bounded transaction page, and only then commits the credentials and device/session state. `oosta-blu check` checks reuse without interactive credentials. `oosta-blu deposit` asks for deposit evidence only. The upstream plaintext store stays disabled. Bank data and credentials are kept off the storefront host.

The AES-256-GCM vault uses a fresh nonce on each write, an authenticated format header, a mode-0600 atomic file replacement and file and directory sync on Linux. The service user owns its mode-0700 state directory. systemd supplies the separate root-only key as a runtime credential. The state directory is the only persistent writable path in the sandbox. A lock prevents overlapping device operations. Missing enrollment is an explicit nonzero result. A returned OTP challenge during renewal records a marker in the encrypted vault and blocks another login attempt until the owner re-enrolls. The HTTP/2 connection closes on exit. The key and vault live on the same host. Privileged host or live process compromise can expose the bank credentials.

Synthetic tests covered successful save and reload, ciphertext without cleartext fields, Linux mode, wrong-key rejection and modified-ciphertext rejection. The tests passed on Windows and the Iran host. Remote checks confirmed the service user cannot read the source key directly, missing enrollment exits with status 3, the old plaintext state file is absent and key exchange completes. The owner reported `BLU_ENROLL_OK rows=5`. A separate noninteractive `oosta-blu check` succeeded with `BLU_SAVED_HISTORY_OK rows=5`. On the Iran host, the encrypted state file was mode 0600, the key was root-owned mode 0400, and the upstream plaintext session file was absent. This check establishes cross-process reuse. It did not establish whether the token was renewed after expiry. This deployment only changes the private probe and creates no scheduled bank logins or payment confirmation.

The first saved-session deposit probe saw 20 rows, 16 credits and one credit matching amount, IBAN and timestamp shape. Detail lookup returned one row, but the expected structured receipt field was absent (receiptFields=0). The diagnosis is that the current probe cannot use the structured receipt contract for this live credit. Whether the bank's display description has a usable identifier is still open. The updated probe checks explicitly labeled tracking and reference lines independently, handles Persian and Arabic digits and bidi markers, preserves leading zeroes and rejects ambiguous or unlabeled numbers. Counts are emitted without text, references or credentials. A textual match is diagnostic only. The structured success criterion and order state are unchanged. Regression passed on Windows and the Iran server.

The owner authorized the follow-up directly from the saved session. A one-off server-side inspection read 20 recent rows, found nine card credits, and fetched details for the first five distinct eligible IDs. All five had a bank description containing explicitly labeled tracking and reference values. None exposed the expected structured receipt or receipt-status field. No bank values were emitted. The saved token changed during the authenticated run, confirming automatic renewal without another owner prompt. The selected historical transaction from the owner's manual test was not identified during this sample.

The revised probe treats the unique explicitly labeled bank tracking value as a separate text match when the structured field is absent. It preserves exact code comparison, rejects disagreement between structured and labeled tracking, rejects reference numbers as tracking, and reports multiple candidate matches as ambiguous. This evidence mode does not establish settlement or update a store order. Synthetic cases passed locally and on the Iran host; the revised probe was installed on that host.
