# Blu shadow observation and claim

The pilot is implemented on the working branch. The live storefront and the live Iran collector have not been updated with this phase. No new signing or HMAC credentials are installed.

The Iran sender accepts one specified invoice amount, receiving IBAN and tracking code in its private terminal. It searches a bounded page of the enrolled receiving account, verifies exact integer-rial amount, card-credit direction, receiver and the bank-provided tracking field or explicitly labeled description. It rejects contradictions in detail amount, currency, destination, direction or time when those fields are supplied by the bank. Some live detail fields remain unverified. The sender emits the amount and timestamps plus three digests. The raw account number, IBAN, transaction ID, tracking value, bank description and personal history are not included. Tracking codes use a separate keyed HMAC on the collector and API to reduce offline guessing risk. The receiver recognizes the account digest using its configured IBAN. The sender signs exact JSON bytes with Ed25519 and only submits them to the fixed HTTPS Oosta endpoint.

The server limits the raw body to 4 KB, checks the signature before decoding JSON, rejects compressed bodies, validates a strict schema and enforces observation freshness. Its private no-store response returns only a status. The endpoint requires all QA configuration and is disabled by default. Only reports associated with the configured QA user and exact invoice destination and amount enter the ledger. The transaction digest cannot change its account, amount, bank time or tracking digest on replay. Matching checks the locked current order, the invoice window and an exact tracking HMAC from a pending owner receipt. Stored observations can be re-evaluated on replay after a receipt arrives.

A unique database claim plus the order lock protects concurrent reports. A competing eligible observation holds the case for review, including distinct codes matching separate pending receipts. Historical claims are retained, while a replay after rejection is only observed. The existing order payment state, stock and delivery are untouched by this endpoint. The HMAC key is separate from the Ed25519 signing key and the encrypted bank-session key. Rotating the HMAC key after using the ledger requires a compatibility plan for retained observations.

Synthetic tests exercised the actual collector wire bytes against HTTP ingestion. They cover missing or tampered signatures, stale and non-credit payloads, wrong account and amount, evidence before receipt, exact concurrent replay, conflicting identity, concurrent competing credits, previously stored competing credits, receipt rejection and preservation of unpaid order state. The disposable database exercises both new migrations. A separate unit fixture tests payload minimization and consistency checks between the two bank responses. The review addressed short-code hashing, competing observations, current receipt eligibility and conflicting collector details.

The next controlled deployment needs the configured QA card and receiving account binding, private key provisioning, and a narrow ingress rule for the existing preview. A real invoice trace must prove the full evidence path before any delivery automation. The current observed credit is not treated as final bank settlement. The shared personal receiving account remains an attribution concern. Restore or rollback requires reconciling retained observations before any future automatic payment transition.
