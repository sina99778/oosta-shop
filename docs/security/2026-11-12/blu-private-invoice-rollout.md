# Private Blu payment-only invoice

Implemented and published release `20261112-blu-private-invoice`. The issuance API is restricted to the current database ADMIN role and to the literal loopback socket inside the API container. Public preview POST stays blocked. The private configuration names one existing ordinary QA profile, a validated bank-bound receiving card and a UUID campaign. Bank card/account binding was read from the Iran host and transferred privately over verified SSH. Its values and the owner name were not printed. The storefront private settings file is mode 0600. The ordinary card checkout flag remains disabled.

One invoice may be issued per normalized campaign. The transaction lock, lookup across owners and fixed amount check prevent duplicate, moved or silently repriced invoices. A changed destination returns a conflict. It uses the existing invoice amount reservation and a 30-minute window. It contains no products or inventory. The fulfillment helper refuses the test invoice, including via the manual receipt approval route. The owner checkout shows a test label, while its bank metadata stays restricted to that owner's payment view.

The isolated regression and full verify passed, as did lint, local production build, production Docker builds and both dependency audits. Tests covered a forged forwarding header, denied non-admin or cross-owner access, a demoted admin, strict request DTO, concurrent repeat, a different profile/destination on the same campaign, amount exhaustion, and refusal of manual approval. Public preview smoke passed after release.

The live invoice `cmwe2e1i80001mt01qt0f3l8w` was issued for exactly 10,000 IRR. It was pending at verification and expires on 2026-11-12 at 22:03:05 UTC. Repeating issuance returned the same ID. Owner access returned 200/private/no-store, non-owner returned 404, and there were no inventory items. No transfer or bank observation was made during issuance. Public Blu ingress and public writes remain blocked. The separate real-bank trace requires a prepared receipt/evidence submission channel before transferring. The before and after database backups preserve the release and this allocation.
