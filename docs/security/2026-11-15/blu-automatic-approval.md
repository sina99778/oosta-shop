# Automatic approval of matched Blu receipts

The owner explicitly requested automatic confirmation after the real Office checkout test. This change reuses the existing receipt approval transaction, order row lock and delivery engine. `BLU_AUTO_APPROVE_ENABLED` defaults to false and is a server setting, not a customer/admin request field. Global public checkout and supplier spending are separate switches and are not enabled by this feature.

Signed event ingestion still validates the receiving-account digest, signature, freshness, CREDIT direction, currency, exact amount, receipt tracking/reference digest, invoice time window and competing observations before persisting a claim. After a match it requests approval for that order. The existing polling job also sweeps persisted matches, so a process failure between claim and approval is recoverable without a new bank request. The sweep processes at most five receipts per invocation with a rotating offset; eligible backlogs can require multiple two-minute polling cycles. Unexpected per-receipt errors are logged with a receipt identifier only and do not stop other approvals or bank discovery; business conflicts leave receipts pending for manual review. Database failures while listing the queue still fail visibly.

Automatic eligibility is rechecked inside the existing approval transaction under the order lock: PENDING_REVIEW, no previous paid timestamp, an ordinary current database user, a current receiving card/IBAN, immutable amount key, valid IRR/IRT conversion and discount, a matching non-review bank claim within the payment window and a 24-hour processing grace. Exactly one INTERNAL plan item and its one RESERVED unit are required. Unreserved or supplier-sourced inventory cannot be fetched or purchased by this worker. The dedicated private-stock QA order additionally retains its linked-attempt/profile/campaign/plan guards. Payment-only QA invoices never deliver. Receipt, paid order, sold inventory and private attempt completion commit together. Other owners cannot read the resulting credential vault, and private responses retain no-store.

The public receipt DTO and authenticated administrator review DTO are unchanged. The automatic flag is passed only by the trusted worker. Customer checkout refreshes every 15 seconds only while awaiting review/delivery and visible; it cleans up polling after payment, on unmount and while hidden. A visibility change triggers a refresh. Existing manual refresh/error UI remains available. No new dependency or database migration is needed.

Test-first evidence: the private-checkout recovery regression initially failed because polling did not approve the matched receipt; manual approval still succeeded. After implementation the isolated suite covered ordinary automatic signed-event delivery, concurrent event replay, the feature-off switch, recovery of persisted evidence, review/reference mismatches, altered destination/amount/expiry, missing reservation, changed buyer role, private QA boundaries and exactly one delivery. The customer effect test initially failed with zero refresh timers; it now verifies refresh, hidden-tab suppression, cleanup and stop-on-PAID. External supplier/bank data and notifications are synthetic in automated tests.

Independent review found that an unexpected failure of one receipt could abort the whole polling cycle. A disposable regression reproduced a real PostgreSQL lock lasting 6.5 seconds and the resulting Prisma P2028 transaction expiry; the old loop aborted. The fix isolates that receipt, continues the other four approvals and recovers the failed receipt on the following poll. No production lock or synthetic production record is used for this test.

Limits: this is evidence collected from an unofficial bank client, not a contractual banking webhook or bank settlement guarantee. A later newly observed conflict cannot retract credentials already disclosed; amount/reference uniqueness and current competing-claim checks reduce that risk but do not establish future settlement finality. Expired sessions, unavailable bank access, ambiguous observations and inventory failures require manual attention. No new real bank transfer or supplier purchase is part of this release; the previous live manual-approval test is not being relabeled an automatic test. No claim is made about every deployed flow being secure.

Local release checks passed: full `npm run verify`, full `npm run lint` and production API/web build. Both `npm audit --omit=dev` and `npm audit` reported zero advisories using the system CA store. The intentional transaction-timeout regression prints the reproduced Prisma error while its assertions and suite pass. Independent review rechecked the failure-isolation fix and reported no remaining blocker; that is a scoped review, not a full system audit.

## Observed deployment

Release `20261115-blu-auto-approval` built API and web images successfully, started healthy and became the current release. The API reports the parsed automatic-approval flag true, while public stock checkout remains false. The existing shared private configuration was backed up before changing only the automatic-approval setting; prior images remain tagged for rollback. A pre-release database archive was captured and its supplier-ledger table listing checked. No new schema migration was required.

Two live sweeps scoped to the already paid Office order returned zero approvals. A subsequent normal polling pass returned zero bank jobs. The original paid timestamp, payment reference, approved receipt, inventory identity and sold timestamp were unchanged. The supplier ledger remains four attempts totaling USD 1.37, and the financial purchase grant is disabled. This is a live replay/no-side-effect check, not a new positive real-money automatic checkout test.

The collector timer remains active and a manual invocation of the same scheduled service returned idle after deployment. The temporary private receipt route remains closed (HTTPS POST returns 503). Public payment configuration still reports online=false and cardToCard=false. Automatic processing is ready for subsequent eligible reserved-stock receipts in the authorized rollout; general public sales have not been enabled. Public storefront availability is checked separately through HTTPS.
