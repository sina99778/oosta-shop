# Customer password recovery

- Customers bind their existing account email from Account security. Enrollment requires a current customer session, the current password, and a code delivered to that email. Confirmation requires the same account and unchanged session version. Historical accounts start unverified. Administrator and phone-only accounts are ineligible.
- The API accepts valid reset requests with the same body and status for unknown, ineligible, and eligible addresses. Delivery happens asynchronously outside the HTTP response. Reset links use a configured storefront origin and carry the token in a URL fragment, which the form clears after reading. The API accepts the token in a private, non-cacheable POST body.
- A challenge lasts 15 minutes. The database stores only the SHA-256 digest of the 256-bit token and the challenge state. The current email must match the verified address at issue and redemption. An atomic transaction consumes the reset token and increments the session version. Existing browser and bearer sessions immediately lose access to protected routes. API keys follow their separate revocation policy.
- In-process per-IP limits apply independently to each recovery operation. Database-backed cooldown and challenge replacement checks apply per account, including across application instances. Repeat requests preserve outstanding links. Definite SMTP authentication or envelope rejection expires the challenge and allows a new request after the cooldown. Uncertain SMTP delivery keeps the original challenge valid until expiry.
- Production enrollment and reset requests require the existing SMTP configuration and an HTTPS `WEB_BASE_URL`. The checked-in configuration leaves `MAIL_ENABLED` disabled by default. With delivery disabled, both requests return an account-independent temporary-unavailability response. The host Nginx preview routes must be installed through the usual HTTPS-only session include. No live SMTP messages were sent during verification.
- The existing SMTP transport sends directly without a durable email queue. A process stop can interrupt delivery, and accepted requests indicate receipt of the request. Reset tokens and enrollment codes are never written into database-backed mail payloads.
- Isolated regressions verify synthetic enrollment, same-account scope, purpose separation, denial for ineligible accounts and origins, no-store responses, expiration, repeated requests, single-use concurrent redemption, password change, and session revocation. Storefront contracts render the two login locales and the recovery forms.
