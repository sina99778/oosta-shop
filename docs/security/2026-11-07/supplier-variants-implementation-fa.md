# تنوع محصولات و استعلام تأمین‌کنندگان — ۲۰۲۶-۱۱-۰۷

## دامنهٔ پیاده‌سازی

این مرحله انتخاب نوع محصول، اتصال کاتالوگ و استعلام برآوردی را پیاده می‌کند. موتور خرید از تأمین‌کننده، پرداخت مشتری برای این اقلام، رزرو موجودی و تحویل خارجی فعال نیستند. تغییرات این مرحله هنوز روی VPS منتشر نشده‌اند؛ مهاجرت فقط روی دیتابیس موقت تست اجرا شده است.

- مشخصات هر پلن شامل نام اشتراک، مدت، دسترسی اختصاصی/اشتراکی/تیمی، اکانت/اینوایت/کد/ارتقا، تحویل خودکار/دستی، ضمانت و مدت و پوشش آن، ریجن و سهمیه است.
- مطابق دستور صریح کاربر، ضمانت نامشخص به «بدون ضمانت» تبدیل می‌شود. منبع بدون ضمانت نمی‌تواند گزینهٔ ضمانت‌دار را تأمین کند.
- مدیر، محصول دقیق هر تأمین‌کننده را به همان تنوع وصل می‌کند. تطبیق نام، مدت، ریجن، سهمیه و پوشش ضمانت نیازمند بررسی مدیر است؛ استخراج خودکار قابل اتکا از متن‌های آزاد فروشنده ادعا نمی‌شود.
- دو حساب Canboso با شناسه و کلید و کاتالوگ مجزا نگهداری می‌شوند. قیمت AItoolify از هزینهٔ فروشنده خوانده می‌شود، نه قیمت خرده‌فروشی.
- هر اتصال به اثرانگشت مشخصات منبع و مشخصات پلن مقید است. تغییر معنایی پلن، تأیید منابع را پاک می‌کند؛ تغییر متن یا شیوهٔ تحویل منبع هم اتصال قبلی را نامعتبر می‌کند. تغییر قیمت/موجودی به‌تنهایی نیازمند تأیید دوباره نیست.
- کاتالوگ بیش از ۶۰ ثانیه، قیمت ارز منقضی، ارز فاقد نرخ، موجودی صفر و منبع ناسازگار از استعلام کنار گذاشته می‌شوند. موجودی نامشخص فقط در حالت صریح سفارش‌پذیر و تحویل دستی قابل استفاده است.

## مسیر فرانت تا بک‌اند

فیلترهای مستقل صفحهٔ محصول از DTO عمومی پلن ساخته می‌شوند. تغییر فیلتر، انتخاب و استعلام قبلی را کنار می‌گذارد. API فقط شناسهٔ پلن و تعداد یک را می‌پذیرد؛ قیمت یا تأمین‌کنندهٔ انتخابی مرورگر مبنای محاسبه نیست. DTO عمومی شامل کلید، اثرانگشت اتصال، متن خصوصی فروشنده یا هزینهٔ عمده نیست. قیمت ذخیره‌شدهٔ قدیمی پلن خارجی نیز قیمت فروش نمایش داده نمی‌شود.

ویرایش مشخصات و اتصال‌ها از schema سخت‌گیرانه و احراز نقش فعلی مدیر در دیتابیس عبور می‌کند. تغییر نقش پس از صدور توکن هم دسترسی مدیریتی را می‌بندد. snapshot مشخصات هنگام ایجاد سفارش داخلی ذخیره می‌شود تا ویرایش عنوان آینده، شرایط سفارش قبلی را تغییر ندهد. تغییر معنایی پلن دارای موجودی یا سفارش مسدود است؛ دسترسی به سفارش متعلق به دیگری ۴۰۴ می‌دهد.

## قیمت و نوسان ارز

درصد سود حدس زده نشده است. تنظیم قیمت پیش‌فرض غیرفعال است. پنل مدیر نرخ مستقل USD و USDT، درصد افزایش، کف سود، هزینهٔ ثابت و زمان اعتبار ۶۰ تا ۹۰۰ ثانیه را می‌گیرد. نرخ‌ها در این مرحله دستی هستند؛ سرویس نرخ لحظه‌ای هنوز انتخاب و متصل نشده است. محاسبه با Decimal انجام می‌شود و مبلغ نهایی به تومان کامل رو به بالا گرد می‌شود، در حالی که واحد ذخیره/API ریال است.

استعلام با کوچک‌ترین زمان اعتبار کاتالوگ/نرخ/۶۰ ثانیه منقضی می‌شود. خروجی صریحاً INDICATIVE و checkoutEnabled=false است. مسیر ایجاد سفارش، پلن خارجی را پیش از ایجاد سفارش یا پرداخت با خطا می‌بندد. این خروجی قرارداد قیمت قطعی یا تضمین موجودی نیست.

## کنترل‌های امنیتی و اصلاحات

- مسیرهای خصوصی، از جمله خطای JSON و پاسخ محدودیت درخواست، no-store دارند. middleware کش خصوصی پیش از parser و محدودیت درخواست قرار گرفت؛ تست ابتدا شکست خورد و سپس پاس شد.
- ترتیب بارگذاری dotenv پیش از وارد کردن ماژول تأمین‌کننده/Prisma اصلاح شد. تست فرایند مستقل با فایل تنظیمات مصنوعی و بدون شبکه/دیتابیس ابتدا شکست خورد و سپس پاس شد.
- اثرانگشت اکنون شیوهٔ تحویل نرمال‌شده و delivery_type را هم پوشش می‌دهد؛ تست تغییر codes به manual ابتدا شکست خورد و سپس پاس شد.
- اتصال ضمانت نامشخص/بدون ضمانت به پلن ضمانت‌دار با تست HTTP بازتولید و مسدود شد.
- اتصال منبع تأییدشدهٔ خودکار به پلن دستی با تست HTTP بازتولید و مسدود شد. همین کنترل هنگام خواندن پیشنهادهای قابل مقایسه هم اعمال می‌شود.
- URL و هدر هر سرویس ثابت است؛ انتقال به URL دیگر مسدود، مهلت دریافت ۱۲ ثانیه و سقف پاسخ ۲ مگابایت است. متن خطای سرویس به کاربر منتقل نمی‌شود. کلیدها در فایل خصوصی خارج از Git می‌مانند؛ مسیر اختیاری SUPPLIER_CREDENTIALS_FILE فقط از محیط سرور خوانده می‌شود.
- به‌روزرسانی کاتالوگ قفل تراکنشی و فاصلهٔ حداقل دارد. خطای دریافت، آخرین snapshot سالم را خراب نمی‌کند؛ snapshot منقضی قابل استعلام نیست.
- همهٔ درخواست‌های تست به تأمین‌کنندگان stub و فقط GET بودند. هیچ خرید، فعال‌سازی، پرداخت واقعی یا اعلان واقعی تلگرام در تست انجام نشد.

## شواهد بررسی

- `npm run verify`: typecheck، قراردادهای وابستگی/فروشگاه/رسید/تأمین‌کننده/رابط/راه‌اندازی، رگرسیون امنیتی و تست دیتابیس موقت.
- تست دیتابیس موقت شامل ۱۵ migration، smoke و رگرسیون‌های موجود، مجوزهای مدیر و مالک سفارش، دو حساب مستقل، نرخ منقضی/مفقود، تغییر موجودی، منع پرداخت و snapshot شرایط سفارش است. دیتابیس کاری reset یا seed نشده است.
- ESLint فایل‌های API و اسکریپت‌های درگیر و lint وب، و build تولید هر دو workspace بررسی شدند.
- هر دو audit با اعتبارسنجی TLS فعال و `NODE_OPTIONS=--use-system-ca` اجرا شدند و صفر آسیب‌پذیری گزارش کردند. تلاش اولیه بدون گواهی سیستم با خطای زنجیرهٔ گواهی شکست خورد؛ TLS غیرفعال نشد. گزارش‌های JSON کنار همین فایل هستند.
- در مرورگر با دادهٔ نمونهٔ محلی، فیلتر ضمانت، غیرفعال شدن ترکیب ناسازگار، پاک کردن فیلتر، انتخاب اینوایت دستی و نمایش استعلام بررسی شد. تصویر در `screenshots/supplier-variants-desktop.png` ذخیره شده است. این بازبینی دسکتاپ است؛ تست انتهابه‌انتهای مرورگری مدیر یا خرید خارجی انجام نشده است.
- بازبینی مستقل سه ایراد بالا را پیدا کرد؛ اصلاحات با رگرسیون شکست‌خورده تأیید شدند. جداسازی دوطرفهٔ دستی/خودکار در بررسی تکمیلی پوشش داده شد.

## محدودیت‌های باقی‌مانده

کالاهای واقعی هنوز به‌صورت انبوه به پلن‌های فروشگاه وصل نشده‌اند؛ متن‌های متناقض، درخواست ارسال رمز حساب و اقلام آزمایشی/OTP/API با محصول اصلی یکی فرض نمی‌شوند. ضمانت متنی فاقد فیلد ساختاریافته طبق سیاست کاربر NONE است؛ پنل این مرحله امکان تبدیل دلخواه ضمانت منبع به ضمانت‌دار ندارد. ضمانت کمتر از یک روز فعلاً نمایش ساختاریافته ندارد و نباید به یک روز گرد شود. پوشش ضمانت و سایر مشخصات متنی هنگام تأیید اتصال باید دستی بررسی شوند.

برای فروش واقعی، اتصال نرخ ارز، تعیین سیاست سود بر اساس هزینه‌های واقعی، quote قطعی مقید به سفارش، کنترل تغییر قیمت، مدیریت نتیجهٔ نامعلوم خرید، جلوگیری از خرید تکراری، تطبیق تراکنش و تحویل امن/بازپرداخت باید در مرحلهٔ جدا پیاده و تست شوند. تست محلی و audit بدون یافته، تضمین نبود باگ یا امنیت کل سامانهٔ مستقر نیست.
