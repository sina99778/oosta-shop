# خرید تأمین‌کننده با مجوز اعتبار فعلی

## مجوز و سیاست

مالک پس از توضیح نبود سقف قیمت upstream، صریحاً ریسک تغییر قیمت تا سقف موجودی فعلی هر ربات را پذیرفت. هیچ شارژ تازه‌ای مجاز یا انجام نشده است. snapshot مجاز: Canboso USD2.409999، PremiKey USD0.009999، Vente USD0.66؛ AItoolify USDT0.02 و ToolsMarket صفر. قیمت مشتری همان قیمت ثابت پذیرفته‌شده با ۳۰٪ سود روی هزینهٔ دلاری در زمان استعلام است؛ تغییر قیمت خرید می‌تواند سود واقعی فروشگاه را کاهش دهد، اما مبلغ مشتری افزایش نمی‌یابد.

## تغییرات و مرزها

- `priceCeiling` همچنان false است؛ قابلیت جداگانهٔ walletExposure به جدول خصوصی `supplier_wallet_budgets` وابسته است. budget عمومی/قابل‌تغییر از HTTP نیست و مقدار اولیه بعد از مصرف خودکار تجدید نمی‌شود.
- تمام اعتبار باقی‌ماندهٔ یک منبع، در تراکنش ایجاد سفارش و پیش از نمایش پرداخت، برای یک reference نگه داشته می‌شود. قفل سطر، چند سفارش/پردازش هم‌زمان را از مصرف مجدد همان اعتبار منع می‌کند. حالت PENDING/UNCERTAIN اعتبار را نگه می‌دارد.
- پیش از ارسال، هویت سفارش، وضعیت paid، نوع و امضای تنوع، موجودی و fingerprint تازه، نرخ/مهلت، wallet فعال و سقف باقی‌مانده بازبینی می‌شوند. افزایش قیمت پیش از POST مانع خرید می‌شود؛ drift فقط در فاصلهٔ آخرین بررسی تا برداشت در محدودهٔ exposure پذیرفته شده است. موجودی بالاتر از مجوز مانع ارسال است.
- هیچ کلاینتی نمی‌تواند supplier، مبلغ، adapter یا هزینهٔ مجاز تعیین کند. DTO خرید همچنان quoteId و روش پرداخت است؛ نقش فعلی USER و مالک سفارش/quote از DB بررسی می‌شوند. endpointها private/no-store هستند.
- Canboso/PremiKey با Idempotency-Key اجباری و Vente با idempotency_key/customer_reference ثابت وصل شدند. Vente از quote واقعی و lookup فقط‌خواندنی استفاده می‌کند. پاسخ خرید، پیش از normalize در بخش خصوصی job ذخیره می‌شود؛ delivery پس از restart از آن بازیابی می‌شود. هیچ POST دوم یا fallback خرید بعد از نتیجهٔ مبهم اجرا نمی‌شود.
- پاسخ گم‌شدهٔ Canboso که پیش از ذخیرهٔ محلی قطع شود از تاریخچهٔ فاقد credential قابل‌بازیابی خودکار نیست؛ اعتبار نگه داشته می‌شود و بررسی دستی لازم است. ToolsMarket به‌علت نبود idempotency مستند buy و AItoolify به‌علت نبود lookup فقط‌خواندنی با reference ما وارد این registry نشدند. کاتالوگ آن‌ها تغییر نمی‌کند.
- schema حساب، مقدار/ارز/شناسه/تعداد و نوع تحویل بررسی می‌شود. ایمیل بازیابی/توضیحات تحویل در inventory خصوصی حفظ و تنها در سفارش paid مالک نمایش داده می‌شود. پاسخ ناشناخته/نوع اشتباه به خرید دوباره منجر نمی‌شود.
- settlement واقعی یک‌بار و همراه با تغییر پایانی order/job ثبت می‌شود. NO_CHARGE معتبر کل رزرو را برمی‌گرداند. سفارش بدون پرداختِ منقضی‌شده تنها در نبود claim یا observation بانکی داخل بازه آزاد می‌شود. READY نامعتبر و هرگز ارسال‌نشده پیش از REVIEW رزروش را آزاد می‌کند.
- Nginx فقط signup، quote/order جدید تأمین‌کننده و آپلود رسید را روی HTTPS باز می‌کند؛ legacy purchase، درگاه mock و POSTهای نامرتبط در حالت preview می‌مانند. مسیر کارت همان مبلغ یکتا و شاهد امضاشدهٔ بانکی موجود است.

## رگرسیون و بازبینی

آزمون اول false بودن available برای adapter دارای walletExposure و بدون priceCeiling را بازتولید کرد. رگرسیون‌های بعدی نادیده‌گرفتن quote واقعی Vente و ذخیره‌نشدن پاسخ قبل از پردازش را بازتولید کردند. بازبینی مستقل دو ایراد رزرو را یافت؛ هر دو RED سپس GREEN شدند: رزرو READY منقضی‌شده برنمی‌گشت، و واریز ثبت‌شدهٔ بدون رسید در expiry از قلم می‌افتاد. بازبینی اصلاح‌ها یافتهٔ مسدودکنندهٔ دیگری اعلام نکرد.

در بررسی نهایی، صدور quote برای تعریف تازهٔ محصول که با fingerprint بازبینی‌شده فرق داشت نیز بازتولید شد (Missing expected rejection). fingerprint اکنون از selection به adapter.quote می‌رود و پیش از صدور قیمت قابل‌پرداخت با دریافت تازه تطبیق داده می‌شود؛ fingerprint غایب هم رد می‌شود. verify کامل، affected lint و build API پس از اصلاح دوباره موفق شدند؛ بازبینی مستقل این اصلاح یافته‌ای نداشت.

مجموعهٔ ساختگی جدید: هم‌زمانی، یک POST، تغییر قیمت پذیرفته‌شده، رد top-up/مجوز خاموش/ارز نامعتبر، هویت اشتباه، JSON نامعتبر، timeout و اعتبار نگه‌داشته، lookup بدون خرید، settlement یک‌باره، انقضای بدون واریز، حفظ واریز پیش از رسید، نمایش owner-only و no-store. بانک/Telegram/مدل/درگاه واقعی در آزمون خودکار فراخوانی نشدند. DB موقت از `npm run test:isolated` ساخته و حذف شد؛ DB کاری seed/reset نشد.

## بررسی‌های محلی

- `npm run verify`: exit0، شامل قراردادهای قبلی و suite جدید wallet؛ پس از اصلاح‌های بازبینی دوباره کامل اجرا شد.
- `npm run lint`: exit0؛ تغییر بعدی فقط regression/format در فایل‌های همان محدوده بود و affected lint پیش از انتشار تکرار می‌شود.
- `npm run build`: API و web موفق، بعد از پایان verify و بدون اجرای هم‌زمان typecheck با build.
- `npm audit --omit=dev`: صفر advisory؛ `npm audit`: exit1، **۱۴ هشدار high** در زنجیرهٔ dev شامل picomatch/micromatch/fast-glob/tinyglobby و مصرف‌کنندگان ESLint. advisory: GHSA-fc5q-39xc-vjpf. نسخه‌های نصب‌شده picomatch2.3.2 و4.0.4 گزارش شده‌اند؛ پیشنهاد force به تغییر ناسازگار نسخهٔ اصلی ابزارها منتهی می‌شود و اجرا نشد. این انتشار advisory-free نامیده نمی‌شود؛ image فعلی node_modules توسعه را هم در خود دارد، هرچند مسیر request این ابزارهای lint را اجرا نمی‌کند. وابستگی‌ای در این تغییر افزوده/به‌روز نشد.
- `git diff --check`: موفق.

بکاپ تازهٔ age-encrypted پیش از migration به پوشهٔ محلی OostaRecovery منتقل و SHA256 تأیید شد: ۱٬۸۷۹٬۳۷۱ بایت، `e7d7d247ce1652601d2888bf7ac70fda6cdfb0184e1d43ad11418c799e23b924`. کپی موقت کانتینر/سرور پس از تطبیق حذف شد. decrypt/restore تازه انجام نشد. timerهای backup و Blu active و آخرین poll با Result=success/idle مشاهده شدند؛ idle اثبات اتصال تازهٔ بانکی یا تسویه نیست.

## محدودیت

سقف داخل سایت سقف قراردادی فروشنده نیست. واریز/تغییر موجودی بیرونی هم‌زمان با آخرین بررسی از کنترل این برنامه خارج است؛ مجوز محلی از اعتبار اولیه بیشتر نمی‌شود. موجودی کافی هنگام quote رزرو upstream ایجاد نمی‌کند؛ کمبود بعدی یا واریز دیرهنگام ممکن است به بررسی/بازپرداخت دستی نیاز داشته باشد. مقدار customer payment ثابت است؛ margin تضمین‌شده نیست و drift زیاد ممکن است سود واقعی را منفی کند. کیفیت واقعی اشتراک‌ها، برداشت واقعی فروشنده، سلامت کلی سیستم و تسویهٔ نهایی بانک با تست‌های ساختگی تأیید نمی‌شوند. در این انتشار خرید یا انتقال واقعی تازه انجام نشده است.
