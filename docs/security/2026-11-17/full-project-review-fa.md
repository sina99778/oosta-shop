# بازبینی کامل پروژه Oosta — ۱۴۰۵/۰۸/۲۶ (2026-11-17)

دید بازبینی: مهندس نرم‌افزار و طراح وب با ۵ سال سابقه. شاخه `codex/oosta-redesign-security-checkpoint`.
این گزارش فقط بازبینی است؛ هیچ کدی تغییر داده نشد.

## بررسی‌هایی که اجرا شد

| بررسی | نتیجه |
|---|---|
| `npm run verify` (typecheck، dependency، contracts، security، isolated DB) | سبز، exit 0، ۴۹ مورد PASS، `fail 0` |
| `npm run lint` (ریشه + web) | بدون خطا |
| `npm run build` (API + Next.js) | موفق |
| `npm audit --omit=dev` و `npm audit` | `found 0 vulnerabilities` |

سبز بودن این‌ها یعنی رفتارهای تست‌شده درست‌اند؛ به این معنی نیست که کل سیستم مستقر بی‌باگ یا امن است.
رابط کاربری در این دور در مرورگر اجرا و دیده نشد؛ بخش طراحی از روی کد است.

## نقاط قوت

- اعتبارسنجی env با Zod و نگهبان‌های production (رد JWT ضعیف، رد mock و sandbox) — `apps/api/src/config/env.ts`.
- نقش کاربر در هر درخواست از دیتابیس خوانده می‌شود، نه از JWT؛ تنزل یا حذف ادمین فوری اعمال می‌شود — `middleware/auth.ts`.
- مسیر پول: قفل سفارش، `FOR UPDATE SKIP LOCKED` برای موجودی، تحویل idempotent، اتصال provider به خود سفارش (جلوگیری از سوئیچ Zarinpal→mock) — `orders.service.ts`، `payments/provider.ts`.
- `Cache-Control: private, no-store` روی همه مسیرهای خصوصی؛ پیام خطای 5xx در production نشت نمی‌کند.
- ورود با hash ساختگی برای کاهش timing enumeration.
- عامل هوش مصنوعی بدون تأیید صریح ادمین چیزی را تغییر نمی‌دهد؛ ربات تلگرام فقط چت خصوصی ادمین را می‌پذیرد.
- بکاپ با `age` رمز می‌شود؛ تست‌ها روی دیتابیس یک‌بارمصرف اجرا می‌شوند.
- رندر Markdown سفارشی است، `dangerouslySetInnerHTML` فقط برای JSON-LD امن‌شده و CSS تم با رنگ‌های hex اعتبارسنجی‌شده.

## یافته‌ها (به ترتیب شدت)

### بحرانی / بالا

1. **خروجی چت شخصی تلگرام در git است.** پوشه `ChatExport_2026-11-05/` (۲۷ مگابایت، ۱۵۵ فایل شامل عکس و ویدیو) track شده. اگر مخزن push یا به کسی داده شود، داده شخصی نشت می‌کند. باید از ایندکس و تاریخچه حذف شود (بازنویسی تاریخچه کار مخربی است و تأیید لازم دارد).
2. **حجم زیادی کار commit نشده است.** ۱۸۲ مسیر تغییرکرده یا untracked، از جمله **۶ migration جدید Prisma** و کل ماژول‌های Blu و suppliers. با خرابی دیسک همه از بین می‌رود و deploy از git بدون این migrationها schema ناقص می‌سازد.
3. **CI وجود ندارد.** پوشه `.github` نیست؛ `verify` فقط وقتی کسی دستی اجرا کند اجرا می‌شود.
4. **توکن در `localStorage` با CSP ناقص.** JWT هفت‌روزه در `localStorage` نگه داشته می‌شود (`apps/web/lib/auth.tsx`) و CSP فقط `frame-ancestors/base-uri/object-src` دارد، بدون `script-src` (`apps/web/next.config.ts`). هر XSS یعنی سرقت توکن و خواندن اکانت‌های تحویل‌شده. پیشنهاد: کوکی `httpOnly; Secure; SameSite`، یا دست‌کم CSP سخت‌گیر با nonce و توکن کوتاه‌عمر همراه refresh.
5. **اطلاعات تحویلی بدون رمزنگاری ذخیره می‌شود.** `accountPassword`، `licenseKey` و `giftCardCode` در `schema.prisma` متن ساده‌اند. پیشنهاد: رمزنگاری در سطح برنامه (AES-GCM با کلید بیرون از DB).
6. **حساب ادمین تنها نقطه شکست است.** ادمین 2FA ندارد. API keyها نقش کامل ادمین دارند و انقضا و scope ندارند. شماره کارت مقصد کارت‌به‌کارت از پنل، ربات و عامل AI به‌صورت زنده قابل تغییر است. یک توکن یا کلید دزدیده‌شده کافی است تا همه پرداخت‌ها به کارت دیگری برود. پیشنهاد: 2FA، کلید با scope و انقضا، و هشدار تلگرامی جداگانه برای هر تغییر تنظیمات درگاه.
7. **بازیابی حساب وجود ندارد.** مسیرهای auth فقط `signup/login/me` هستند. فراموشی رمز، تغییر رمز و خروج از همه دستگاه‌ها پیاده نشده؛ با تغییر رمز هم توکن‌های قبلی باطل نمی‌شوند.

### متوسط

8. **Docker:** کانتینرها با root اجرا می‌شوند (دستور `USER` نیست). runtime کل `node_modules` را با devDependencies کپی می‌کند. برای api و web healthcheck تعریف نشده. `prisma migrate deploy` هنگام start اجرا می‌شود و با چند نمونه همزمان race دارد.
9. **TLS و HSTS:** بلوک SSL در `deploy/nginx/default.conf` کامنت است و HSTS تعریف نشده. اگر TLS فقط روی CDN خاتمه می‌یابد، این وابستگی باید مستند و بررسی شود.
10. **فایل‌ها در Postgres ذخیره می‌شوند:** تصاویر محصول، رسیدها و رسانه بلاگ `bytea` هستند. نتیجه: DB و بکاپ بزرگ‌تر، و هر درخواست تصویر از Node و DB رد می‌شود. نوع فایل از هدر کلاینت خوانده می‌شود و magic bytes بررسی نمی‌شود (`nosniff` خطر را کم می‌کند).
11. **state در حافظه:** rate limiter و `pendingActions` عامل AI در حافظه پروسه‌اند؛ با ری‌استارت پاک می‌شوند و برای چند نمونه کار نمی‌کنند. محدودیت ورود فقط بر اساس IP است و حمله توزیع‌شده روی یک حساب را نمی‌گیرد.
12. **پرداخت آنلاین:** موجودی هنگام ساخت سفارش رزرو نمی‌شود. خریدار ممکن است پول بدهد و به `PAID_PENDING_FULFILLMENT` و بازپرداخت دستی برسد. برای کالای کم‌موجود، رزرو کوتاه‌مدت پیشنهاد می‌شود.
13. **پیچیدگی کد در مسیر پول:**
    - فایل‌های بزرگ: `admin.service.ts` (۱۱۱۰ خط)، `agent.ts` (۸۲۳)، `bot.ts` (۷۶۷).
    - منطق ویژه QA و Blu وسط `deliverOrderInTransaction` آمده؛ حساس‌ترین تابع سیستم پر از شاخه‌های خاص شده است.
    - importها قبل از کامنت سرفایل آمده‌اند (`app.ts:1`، `admin.routes.ts:1`، `orders.service.ts:1`)؛ نشانه وصله‌کاری خودکار.
    - پیشنهاد: Blu را پشت یک استراتژی یا adapter جدا کنید.
14. **تست:** تست‌ها اسکریپت‌های Node سفارشی‌اند، بدون اندازه‌گیری coverage و بدون تست E2E مرورگری (مثل Playwright) برای خرید، ورود و پنل.
