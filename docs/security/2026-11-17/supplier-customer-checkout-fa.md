# اتصال مشتری، پرداخت و تأمین — ۲۰۲۶-۱۱-۱۷

ادامهٔ [موتور تأمین](supplier-fulfillment-engine-fa.md). هدف این دور اتصال واقعی کدهای فرانت/API/پرداخت/تحویل، با فروشنده و بانک ساختگی در آزمون‌هاست؛ مجوز خرج تازه یا فعال‌سازی برداشت زنده از ربات‌ها فرض نشد.

## رفتار متصل‌شده

- قیمت قابل‌خرید در `SupplierCheckoutQuote` با مالک، پلن، امضای variant، مبلغ IRR، شرایط خصوصی فروشنده و انقضا ذخیره می‌شود. هیچ قیمت، محصول جایگزین، اطلاعات فروشنده یا adapter از body خرید پذیرفته نمی‌شود؛ DTO خرید فقط quoteId و روش مجاز پرداخت دارد.
- quote یک‌بار و تحت قفل مصرف می‌شود؛ سفارش PENDING و رکورد AWAITING_PAYMENT در همان تراکنش ساخته می‌شوند. درخواست هم‌زمان/تکراری برای همان quote سفارش یا جلسهٔ پرداخت دیگری نمی‌سازد. gateway initialization در خارج تراکنش انجام می‌شود؛ خطای مبهم آن به ساخت خودکار جلسهٔ دوم منجر نمی‌شود.
- پرداخت آنلاین از همان abstraction و محدودیت mock در production استفاده می‌کند. تأیید مبلغ/ارز/authority و context با provider ثبت‌شدهٔ سفارش انجام می‌شود. callback عمومی فقط status/orderId می‌دهد. پیش از paidAt/ref معتبر، worker خریدی نمی‌فرستد؛ پس از تأیید، سفارش paid/pending و job READY می‌شوند.
- کارت‌به‌کارت فقط با verifier/destination معتبر، تأیید خودکار Blu روشن و فرصت کافی از اعتبار quote پیشنهاد می‌شود. مبلغ یکتا و تخفیف جزئی همان allocator قبلی استفاده می‌شود؛ مبلغ واقعی پیش از واریز در صفحهٔ کارت نمایش داده می‌شود. expiry صورتحساب همان expiry quote است و قیمت پایه/تخفیف/مبلغ نهایی با هم تطبیق داده می‌شوند.
- آپلود رسید کارت، tracking/reference عددی معتبر می‌خواهد. عکس رسید به‌تنهایی اجازهٔ خرید نمی‌دهد. هم تأیید دستی و هم خودکارِ سفارش تأمین‌کننده به claim بانکی امضاشده/بدون ابهام، مقصد/مبلغ/زمان صحیح، مالک USER، quote و job درست و receipt منطبق نیاز دارند. receipt، paidAt/ref و READY شدن job در یک تراکنش ثبت می‌شوند.
- پیش از ارسال purchase و پیش از انتشار credential، شاهد بانکی جاری و receipt APPROVED دوباره تحت قفل سفارش کنترل می‌شوند. مبهم‌شدن شاهد یا رد رسید پس از تأیید اولیه می‌تواند خرید/تحویل را به REVIEW ببرد.
- worker محدود پنج‌تایی، READY را یک‌بار dispatch و وضعیت‌های مبهم را فقط lookup می‌کند. زمان آخرین تلاش حتی در شکست lookup به‌روزرسانی می‌شود تا پنج خطای قدیمی صف را برای همیشه قفل نکنند. worker هنگام shutdown متوقف می‌شود و با registry خالی اصلاً شروع نمی‌شود.
- پنل قیمت موجود، INDICATIVE یا FIRM را می‌پذیرد. دکمهٔ پرداخت فقط برای quote همان پلن/حساب، مبلغ معتبر، مهلت معتبر و روش مجاز ظاهر می‌شود. تغییر نشست/پلن، پنل قبلی را remount می‌کند؛ پاسخ پس از unmount نمی‌تواند کاربر را redirect کند. فقط quoteId/method به سرور ارسال می‌شود. زمان پایان اعتبار، ارسال تکراری و پیام خطا کنترل شده‌اند؛ استایل سرمه‌ای/نعنایی و اجزای موجود حفظ شدند.

## مرزهای امنیتی و سازگاری

createApp فقط از آرگومان داخلی سرور adapter می‌گیرد. endpoint یا تنظیم محیط برای تزریق adapter ساختگی اضافه نشده است. production آن را بدون آرگومان می‌سازد؛ registry زنده خالی می‌ماند. بنابراین FIRM checkout و خرید/worker زنده فعال نیستند؛ قیمت برآوردی قبلی همچنان کار می‌کند.

namespace جدید `/supplier-checkout` احراز هویت و private/no-store دارد. همان middleware جاری، role و sessionVersion را از DB می‌خواند و نوشتن با cookie را از نظر Origin کنترل می‌کند. کد صدور quote و مصرف آن نقش فعلی و مالکیت را هم بررسی می‌کند. قیمت خصوصی upstream، token آن و دادهٔ تحویل در DTO قیمت نیستند. vault موجود همچنان مالک200، دیگران404 و ناشناس401 است. بدنه‌های خرید strict هستند.

مسیرهای stock داخلی و QA بانک حذف یا آزاد نشدند؛ branch جداگانهٔ supplier فقط برای صورتحساب دارای flag و رابطهٔ quote/job معتبر کار می‌کند. jobهای پرداخت‌نشده در sweep انتخاب نمی‌شوند. marker یا receipt جعلی بدون شاهد بانکی کافی نیست. منطق callback قدیمی برای سفارش فاقد quote تأمین‌کننده همچنان همان مسیر قبلی است.

migration جدید صرفاً جدول quote و حالت AWAITING_PAYMENT را اضافه می‌کند. migration موتور قبلی تغییر نکرد. دیتابیس واقعی seed/reset نشد. کد تست فقط روی دیتابیس یک‌بارمصرف اجرا می‌شود و برای این مجموعه connection_limit=1 حفظ شده است.

## شواهد آزمون و رفع ایراد

رگرسیون HTTP ابتدا نبود مسیر امن را با 404 به‌جای401 بازتولید کرد. تست UI ابتدا نبود guard قیمت قابل‌خرید را نشان داد. سپس مسیر آنلاین با mock gateway و registry ساختگی از quote تا vault موفق شد؛ استعلام ناشناس، quote متعلق به دیگری، تغییر مبلغ در body، authority ناشناخته، callback ناموفق، session تکراری، expiry قبل و بعد از آغاز پرداخت و بازیابی در نمونهٔ تازهٔ برنامه بررسی شدند.

کارت‌به‌کارت از quote طولانی تا صورتحساب، receipt، wire امضاشدهٔ ساختگی، تأیید بانکی و خرید/تحویل worker آزموده شد. امضای غلط، مبلغ غلط و تأیید دستی بدون claim رد شدند. replay خرید دوم نساخت. کنترل‌های مستقل مقدار/مقصد/quote/نقش/مرجع/reviewRequired/زمان/ارز/وضعیت job همگی قبل از تأیید receipt رد شدند.

ایرادهای بازتولید و اصلاح‌شده:

1. quote مصرف‌شدهٔ منقضی، link پرداخت را دوباره می‌داد (201 به‌جای409). اکنون جلسهٔ پرداخت‌نشدهٔ منقضی باز نمی‌شود و سفارش پرداخت‌شده هم لینک دوبارهٔ درگاه ندارد.
2. پنج lookup ناموفق صف را اشغال می‌کردند؛ سفارش ششم paid/pending می‌ماند. ثبت زمان تلاش، نوبت سفارش‌های بعدی را حفظ کرد؛ regression سپس خرید ششم را بدون برداشت دوم تأیید کرد.
3. صورتحساب رهاشده پس از انقضا خرید بعدی را برای همیشه می‌بست (409 به‌جای201). اکنون expiry بدون claim، مانع ایجاد صورتحساب تازه نیست؛ key و سابقهٔ قبلی حفظ می‌شوند و claim موجود همچنان برای بررسی نگه داشته می‌شود.
4. تغییر reviewRequired پس از تأیید receipt و قبل از worker، همچنان purchase می‌فرستاد (شمار2 به‌جای1). بازبینی شاهد بانکی در موتور این مسیر را متوقف می‌کند.
5. fixture راه‌اندازی بعد از افزودن worker، locals جدید app را نداشت؛ fixture به‌روزرسانی شد و حالا اجرای start worker هم بدون DB/network واقعی assert می‌شود.
6. با registry قابل‌خرید، تحویل دستی به‌جای برگشتن به قیمت برآوردی 409 می‌گرفت. رگرسیون 409 به‌جای200 را بازتولید کرد؛ اکنون checkout آن نوع را unavailable اعلام می‌کند و endpoint قبلی استعلام برآوردی را حفظ می‌کند. verify کامل و build API پس از این اصلاح دوباره موفق شدند.

هیچ supplier، بانک، gateway پولی، مدل یا Telegram واقعی در آزمون‌ها صدا زده نشد. mock provider در DB یک‌بارمصرف صریح انتخاب شد. اطلاعات تحویل و بانک ساختگی‌اند. تست موفق، کیفیت اکانت تجاری یا امنیت کامل سیستم را ثابت نمی‌کند.

## بررسی‌ها

- `npm run verify`: exit0، شامل همهٔ مجموعه‌های قبلی و مسیر آنلاین/کارت جدید؛ trigger و timeoutهای عمدی آزمون‌ها خطای انتظاررفته‌اند.
- `npm run lint`: exit0 و بدون warning باقی‌مانده در پنل جدید.
- `npm run build`: API و web موفق، بعد از پایان verify.
- `npm audit --omit=dev` و `npm audit`: هر دو صفر advisory با بررسی TLS و CA سیستم.
- `git diff --check`: موفق.
- بازبینی مستقل کد، ایرادهای صف و expiry را شناسایی کرد و پس از اصلاح/رگرسیون، یافتهٔ اجرایی باز دیگری اعلام نکرد؛ runtime یا سرویس واقعی را مستقلاً اجرا نکرده است.

## محدودیت عملیاتی

خرید زنده، رفتار واقعی gateway و برداشت واقعی تأمین‌کننده در این مرحله آزموده نشده‌اند. provider زندهٔ تأمین‌کننده باید سقف برداشت، idempotency و lookup قابل‌اعتماد داشته باشد یا سیاست ریسک مالی دیگری جداگانه طراحی و مجاز شود؛ این انتشار چنین ریسکی را خودکار قبول نمی‌کند. host nginx برای خرید عمومی باز نشده است.

قیمت قابل‌خرید حداکثر پانزده دقیقه و کوتاه‌تر از مهلت فروشنده/نرخ است؛ ضمانت رزرو موجودی upstream از این کد نتیجه نمی‌شود. نبود موجودی/quote معتبر پس از واریز به بررسی/بازپرداخت دستی نیاز دارد. API بانک فعلی اثبات مستقل تسویهٔ نهایی نیست؛ کنترل امضای منبع و تطبیق دقیق انجام می‌شود. refund خودکار بانکی اضافه نشد. credentialهای DB مانند vault فعلی plaintext هستند، بکاپ‌ها age-encrypted می‌مانند.

قبل از انتشار، آرشیو رمز‌شدهٔ تازه در پوشهٔ محلی OostaRecovery کپی و تطبیق SHA-256 تأیید شد؛ ۱٬۸۷۹٬۲۷۴ بایت، hash `6f8c77d5e79e9fa55e55dc02e07f1f78a55e9fc67159a9ac46276c04a5bba9e9`. این نسخه در این مرحله decrypt/restore نشد. نتیجهٔ عملیاتی استقرار و CI پس از مشاهده جدا ثبت می‌شود.
