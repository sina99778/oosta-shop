# آمادگی عملیاتی انتشار — ۲۰۲۶-۱۱-۱۷

## نتیجهٔ نهایی CI

اجرای واقعی [GitHub Actions شمارهٔ 44069641195](https://github.com/sina99778/oosta-shop/actions/runs/44069641195) برای commit `2a98334` با `conclusion=success` تمام شد؛ verify، lint، build، تست backup و هر دو audit موفق شدند. دو اجرای قبلی شواهد شکست‌اند: ابتدا import قراردادها DATABASE_URL نداشت، سپس PostgreSQL بستهٔ Ubuntu نتوانست در مسیر سیستمی سوکت بسازد. محیط CI اکنون URL/JWT ساختگی دارد؛ runner یک‌بارمصرف در POSIX فقط TCP استفاده می‌کند و در شکست daemon لاگ دیتابیس ساختگی را هم نشان می‌دهد. اجرای دوبارهٔ isolated در Windows هم موفق بود. بازبینی مستقل اصلاح‌ها یافتهٔ باز دیگری نداشت.

مالک در پاسخ نهایی گفت هنوز بودجه را نمی‌داند و باید ربات‌ها را جدا شارژ کند. خرید یا بازکردن پرداخت با سقف نامعلوم انجام نشد. برای شروع محدود لازم نیست همهٔ ربات‌ها شارژ شوند؛ تأمین یک کالای معتبر و تعیین سقف عددی هنوز باقی است.

## دامنه

این مرحله اسکریپت بررسی انتشار، CI و بکاپ زمان‌بندی‌شده را تکمیل می‌کند. کد اجرایی فرانت، API، DTO، schema یا احراز هویت تغییر نکرد؛ هیچ migration، خرید، پرداخت یا فعال‌سازی عمومی انجام نشد. استایل سرمه‌ای/نعنایی حفظ شد. endpointهای خصوصی، نقش جاری و سیاست no-store در smoke عمومی دوباره بررسی شدند؛ رگرسیون‌های خرید، تحویل و بازپرداخت فقط روی دیتابیس یک‌بارمصرف اجرا شدند.

## آزمون انتشار

`scripts/preview-http-check.cjs` قبلاً فایل fingerprinted را به‌اشتباه ملزم به no-store می‌کرد. آزمون ساختگی HTTP ابتدا این شکست را بازتولید کرد. اکنون فقط همان درخواست asset باید public/immutable باشد؛ باقی بررسی‌ها همچنان no-store می‌خواهند. رگرسیون همچنین پاسخ خصوصی با public cache و asset فاقد immutable را رد می‌کند و به `test:contracts` اضافه شد. تست عمومی بدون حذف هیچ assertion با گزینه‌های login، admin-catalog، supplier-quotes و supplier-qa موفق بود؛ نوشتن عمومی سفارش همچنان بسته است.

## CI

workflow در `.github/workflows/quality.yml` برای push و pull request تعریف شده؛ مستندات تنها از اجرای دوباره معاف‌اند. دسترسی contents فقط read است و checkout credential ذخیره نمی‌کند. checkout و setup-node به SHA تأییدشدهٔ tag رسمی v5 قفل شدند. از Node 24، Prisma generate، ابزار PostgreSQL runner و دیتابیس یک‌بارمصرف استفاده می‌شود؛ دیتابیس production یا secret خدمات در اختیار job نیست.

verify، lint، production build، تست ساختگی backup و هر دو audit اجرا می‌شوند؛ شکست هر مورد job را قرمز می‌کند. فایل YAML محلی parse و دسترسی محدود آن بررسی شد. نتیجهٔ اجرای واقعی GitHub پس از push جدا ثبت می‌شود؛ موفقیت محلی به‌معنی موفقیت CI اعلام نمی‌شود.

## بکاپ روزانه

- `deploy/ops/oosta-backup` از helper موجود `createEncryptedBackup` در کانتینر API استفاده می‌کند. دادهٔ SQL مستقیم فشرده و با age رمز می‌شود؛ آرشیو plaintext روی میزبان ایجاد نمی‌شود. کلید خصوصی بازیابی روی سرور کپی نشد.
- flock از اجرای هم‌زمان جلوگیری می‌کند. فایل موقت فقط پس از کپی موفق، بررسی header فرمت، مجوز 0600 و انتشار اتمی نام نهایی می‌گیرد. دایرکتوری مقصد 0700 است.
- حذف ۳۰روزه فقط فایل‌های نهایی با الگوی همین runner را، پس از ساخت موفق نسخهٔ جدید، شامل می‌شود. فایل‌های نامرتبط حذف نمی‌شوند. در خطا فایل موقت محلی و ciphertext موقت داخل کانتینر پاک می‌شوند.
- مسیر برگشتی کانتینر قبل از استفاده به `/tmp/oosta-backup-<alphanumeric>/oosta-<timestamp>.sql.gz.age` محدود می‌شود؛ مسیر غیرمنتظره رد می‌شود.
- تست‌های shell با docker ساختگی، موفقیت، مجوزها، خطای تولید، مسیر نامعتبر، خطای copy، قفل هم‌زمان و مرز retention را پوشش دادند. هیچ تماس دیتابیس/تلگرام واقعی در این تست‌ها انجام نمی‌شود.
- service و timer پس از `systemd-analyze verify` نصب شدند. اولین اجرای واقعی `Result=success / ExecMainStatus=0` داشت؛ timer روزانه در ساعت ۰۳:۱۵ UTC با تأخیر تصادفی حداکثر ۱۵ دقیقه فعال است. runner زمان حداکثر ۳۰۰ ثانیه دارد.
- اولین ciphertext `oosta-daily-20261117T105233Z.sql.gz.age`، ۱٬۸۷۹٬۲۸۷ بایت، با مجوز 0600 ساخته و به پوشهٔ محلی OostaRecovery کپی شد. SHA-256 هر دو نسخه یکسان بود: `76f7b0342370c55b1696359176c62dd9d03a6d77ee0d965ec600b088d9ca3a3f`.
- این آرشیو جدید در این مرحله decrypt/restore نشد؛ آزمون بازیابی ساختگی و بررسی رمزگشایی آرشیو قبلی در [گزارش بکاپ رمز‌شده](../2026-11-16/encrypted-backups.md) ثبت‌اند.

کنترل وضعیت:

```bash
systemctl status oosta-backup.timer oosta-backup.service --no-pager
journalctl -u oosta-backup.service --no-pager -n 20
```

غیرفعال‌کردن زمان‌بندی بدون حذف آرشیوها:

```bash
systemctl disable --now oosta-backup.timer
```

بکاپ‌های بعدی خودکار فقط روی همین سرور ذخیره می‌شوند؛ فقط نسخهٔ مشاهده‌شدهٔ امروز خارج از سرور کپی شد. برای تحمل خرابی کل VPS، مقصد خارج از سرور و انتقال زمان‌بندی‌شدهٔ آن هنوز لازم است. ارسال زمان‌بندی‌شدهٔ تلگرام همچنان خاموش است و تنظیم توکن تغییر نکرد.

## بررسی فضای دیسک پس از انتشار

1. پس از تأیید سلامت نسخهٔ جدید، فضای آزاد را با `df -h /` و مصرف کش را با `docker buildx du --verbose` بررسی کنید.
2. اگر فضا کم است، رکوردهای قابل‌بازیابیِ بیلدهای تمام‌شده را با شناسهٔ مشخص پاک کنید. برای هر رکوردِ تأییدشده از `docker buildx prune --filter "id=<CACHE_ID>"` استفاده کنید. ایمیج نسخهٔ فعال و نسخهٔ بازگشت، آرشیوهای بکاپ و لاگ‌های عملیاتی را حفظ کنید.
3. دوباره `df -h /` را اجرا کنید و فضای واقعاً آزاد، سلامت API و صفحهٔ اصلی را ثبت کنید. نسخهٔ Buildx روی VPS از `--min-free-space` و `--max-used-space` پشتیبانی می‌کند. نتیجهٔ میزبان را با `df` بسنجید.

پس از انتشار مرحلهٔ دوم، پاک‌سازی کش بیلدهای قبلی فضای آزاد را از ۱٫۸ به ۳٫۰ گیگابایت رساند. سلامت API و صفحهٔ اصلی بعد از عملیات تأیید شد. در بازبینی ۲۲ نوامبر ۲۰۲۶، سرور همچنان ۳٫۰ گیگابایت فضای آزاد داشت.

## مخزن و نتیجهٔ بررسی‌ها

۱۵۵ فایل ChatExport از tracking جدید حذف و الگوی آن ignore شد؛ خود فایل‌های مرجع محلی حفظ شدند. محتوای commitهای قدیمی همچنان در تاریخچه است؛ تاریخچه rewrite یا force-push نشد.

- `npm run verify`: exit 0، شامل تست جدید smoke و دیتابیس یک‌بارمصرف.
- `npm run lint`: exit 0.
- `npm run build`: API و web موفق، exit 0.

- timer جمع‌آوری Blu فعال و آخرین service موفق بود؛ این بررسی، پرداخت یا فروش واقعی جدید نیست.

## مانع فروش واقعی
