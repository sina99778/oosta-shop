# موتور داخلی تأمین و تحویل — ۲۰۲۶-۱۱-۱۷

## پیاده‌سازی و مرز فعال‌سازی

مالک ادامهٔ پیاده‌سازی مسیر خرید خودکار را با تست ساختگی خواست. هیچ مجوز جدیدی برای خرج اعتبار، شارژ کیف پول، خرید اشتراک یا پرداخت واقعی فرض نشد و هیچ‌کدام انجام نشد.

مدل افزودهٔ `SupplierFulfillment` یک رکورد برای هر سفارش، شناسهٔ ثابت خرید، پیشنهاد پذیرفته‌شده، سقف هزینه، ارز، مهلت، وضعیت و نتیجهٔ خصوصی بازیابی نگه می‌دارد. قیدهای DB، سفارش/شناسهٔ درخواست و شناسهٔ سفارش فروشنده را یکتا و هزینه‌ها را مثبت می‌کنند. migration فقط جدول جدید و رابطه با سفارش می‌سازد؛ دادهٔ قبلی را تغییر نمی‌دهد.

سرویس داخلی سه عملیات دارد: آماده‌سازی سفارش پرداخت‌شده، ارسال یک‌باره و بازیابی فقط با lookup. هیچ route HTTP، body، کلید تنظیمات یا DTO برای ثبت adapter اضافه نشد. registry واقعی خالی است؛ فقط فراخوانندهٔ داخلی مورداعتماد می‌تواند adapter بدهد. تنها adapter دارای هر سه تضمین سقف هزینهٔ قابل‌اعمال نزد فروشنده، idempotency و lookup پذیرفته می‌شود.

بررسی مستندات رسمی [OpenAPI ونته](https://web-production-1c7b1.up.railway.app/api/reseller/openapi.json) نشان داد quote قفل قیمت/موجودی نیست و بدنهٔ خرید عادی سقف برداشت ندارد. تجربهٔ موفق API-test جای این تضمین را نمی‌گیرد. این مرحله adapter زندهٔ debit-capable اضافه یا فعال نکرد.

**این مرحله کل خرید عمومی را فعال نمی‌کند.** endpoint ایجاد سفارش فعلی همچنان پلن SUPPLIER را قبل از پرداخت رد می‌کند. پاسخ قیمت عمومی همچنان INDICATIVE و checkoutEnabled=false است. فرانت، Zod/DTO سفارش و handlerهای پرداخت/رسید تغییر نکردند. اتصال بعدی به checkout باید صدور قیمت قابل‌خرید، ثبت قطعی پرداخت و فراخوانی worker را با adapter موردتأیید کامل کند. هیچ پرداخت یا نقش کاربری در این مرحله جعل نشد.

## کنترل‌های مسیر

- آماده‌سازی فقط برای سفارش تک‌قلم/یک‌واحد، IRR، منبع SUPPLIER، کاربر با نقش جاری USER، paidAt و paymentRefId ثبت‌شده و وضعیت PAID_PENDING_FULFILLMENT مجاز است. پلن/محصول باید فعال و snapshot نوع/مدت دقیقاً مطابق variant جاری باشد. مسیرهای دعوت/فعال‌سازی دستی که ورودی اختصاصی لازم دارند پذیرفته نمی‌شوند.
- از همان تطبیق نوع دسترسی، مدت، ضمانت، تحویل، fingerprint و تازگی کاتالوگ موجود استفاده می‌شود. نرخ تازه و سود سیاست فعلی (۳۰٪ روی هزینهٔ ارزی در پیکربندی فروشگاه) در قیمت‌گذاری دخیل‌اند.
- همهٔ استعلام‌های محدودِ قابل‌قبول گرفته می‌شوند و انتخاب با قیمت واقعی quote و نرخ همان ارز انجام می‌شود. نبود نرخ یک ارز، پیشنهاد ارز دیگر را حذف نمی‌کند. مبلغ quote انتخاب‌شده باید در مبلغ پرداخت‌شدهٔ مشتری جا بگیرد؛ قیمت ذخیره‌شدهٔ کاتالوگ به‌تنهایی ملاک انتخاب نیست.
- قبل از شبکه، SENDING در DB commit می‌شود. دوباره‌خوانی READY/SENDING/PENDING/UNCERTAIN هرگز POST جدیدی برای بازیابی نمی‌فرستد. crash بین ثبت SENDING و POST نیز فقط با lookup/بررسی دستی بازیابی می‌شود؛ liveness فدای جلوگیری از برداشت دوباره شده است.
- NOT_FOUND اثبات عدم برداشت نیست و به UNCERTAIN می‌رسد. خطای شبکه خرید دوم ایجاد نمی‌کند. NO_CHARGE پس از گزارش قبلی برداشت، آن را پاک نمی‌کند و به REVIEW می‌رود. refund خودکار یا تعویض خودکار فروشنده پس از debit مبهم وجود ندارد.
- پاسخ باید مرجع، محصول، تعداد، ارز، مبلغ، شناسهٔ سفارش و نوع credential معتبر داشته باشد. مبلغ بالاتر از سقف، ارز/هویت اشتباه، دادهٔ ناقص، تغییر variant و سفارش بسته/بازپرداخت‌شده تحویل را متوقف می‌کنند.
- تحت همان قفل سفارش، ساخت یک موجودی SOLD، وضعیت PAID سفارش و DELIVERED رکورد خرید یک تراکنش هستند. paidAt و paymentRefId قبلی بازنویسی نمی‌شوند. خطای ذخیره‌سازی اجازهٔ نمایش تحویل ناقص نمی‌دهد؛ lookup همان خرید برای بازیابی کافی است.
- خلاصهٔ سرویس فقط id/state/chargedCost دارد. result خصوصی ممکن است دادهٔ تحویل را برای بازیابی نگه دارد؛ به DTO عمومی/ادمین اضافه نشده و از API قابل دریافت نیست. داده در DB مانند vault فعلی plaintext است؛ رمزنگاری در حالت سکونِ همهٔ داده‌های تحویلی موضوع جداست. بکاپ‌ها همچنان age-encrypted هستند.

## شواهد آزمون

تمام داده‌ها، کاربران، قیمت‌ها، adapterها، پرداخت‌ها و پاسخ‌های فروشنده ساختگی و تنها دیتابیس یک‌بارمصرف بودند. هیچ Telegram، بانک، مدل پولی، API خرید واقعی یا gateway واقعی در این تست‌ها فراخوانی نشد؛ دیتابیس کاری seed/reset نشد.

رگرسیون‌ها شامل رد سفارش پرداخت‌نشده، نقش نامعتبر، snapshot متفاوت و تضمین ناقص؛ انتخاب ارزان‌ترین پیشنهاد؛ تغییر قیمت cached11 به quote7 در برابر رقیب8؛ نرخ USD بدون USDT؛ expiry و تغییر variant؛ اجرای هم‌زمان سه worker با فقط یک اتصال دیتابیس و یک purchase؛ جلوگیری از تحویل دوم؛ رد مبلغ/هویت/ارز/credential اشتباه؛ refund حین خرید؛ عدم برداشت قطعی، pending، timeout، crash و lookup بعد از NOT_FOUND هستند.

یک trigger ساختگی نوشتن نهایی DELIVERED را عمداً شکست داد: inventory و وضعیت سفارش rollback شدند، رکورد خرید SENDING ماند، process مجدد purchase دیگری نفرستاد و lookup تحویل را بازیابی کرد. تست مالکیت با API واقعی برنامه روی همان DB ساختگی، مالک200/no-store، ناشناس401 و کاربر دیگر404 را تأیید کرد. دادهٔ تحویل در summary نبود.

### ایرادهای بازتولیدشده و رفع‌شده

1. در نسخهٔ نخست، قیمت ذخیره‌شده می‌توانست فروشندهٔ ارزان‌تر در quote تازه را کنار بگذارد. assertion انتخاب فروشنده ابتدا شکست خورد؛ مقایسه و کنترل توان پرداخت بعد از دریافت quote انجام می‌شود.
2. نبود نرخ USDT پیشنهاد USD را هم متوقف می‌کرد؛ آزمون ابتدا PRICING_UNAVAILABLE گرفت و اکنون پیشنهاد معتبر USD باقی می‌ماند.
3. کاتالوگ با اتصال global درون تراکنش خوانده می‌شد؛ تست connection_limit=1 به pool timeout رسید. `catalogs` اکنون client تراکنش را می‌پذیرد و dispatch همان tx را استفاده می‌کند. همان regression اکنون موفق است.

بازبینی مستقل کد این موارد را مطرح کرد؛ پس از اصلاح، یافتهٔ اجرایی باز دیگری اعلام نشد. بررسی مستقل runtime یا قرارداد واقعی فروشنده را اجرا نکرده است.

## کنترل انتشار و محدودیت

- `npm run verify`: موفق، exit0؛ شامل migration و همهٔ رگرسیون‌های جدید در `test:isolated` با connection_limit=1 و pool_timeout=3. خطای trigger ساختگی و timeout کنترل‌شدهٔ تست قدیمی در خروجی مورد انتظارند و runner با PASS پایان یافت.
- `npm run lint` و ESLint فایل‌های API/runner جدید: موفق.
- `npm run build`: API و web موفق، exit0؛ build بعد از verify اجرا شد.
- `npm audit --omit=dev` و `npm audit`: هر دو صفر advisory، با CA سیستم و بدون غیرفعال‌کردن بررسی TLS.
- `git diff --check`: موفق.

این تغییر هنوز روی production مستقر یا migration آن روی دیتابیس اصلی اعمال نشده است. فعال‌سازی خرید عمومی و اتصال به vendor زنده انجام نشد. موفقیت تست‌های ساختگی نه کیفیت اکانت واقعی را اثبات می‌کند، نه نبود همهٔ باگ‌ها و نه امنیت کامل سیستم مستقر را.
