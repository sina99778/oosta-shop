# بکاپ روزانه در تلگرام — ۲۰۲۶-۱۱-۱۷

مالک صریحاً خواست بکاپ روزانه به ربات ادمین ارسال شود و آرشیو روزانه روی سرور فضا نگیرد. این تغییر جایگزین نگهداری روزانهٔ محلی در گزارش release-operations است؛ هیچ تغییر توکن یا مقصدی انجام نشد.

## رفتار و دامنه

همان systemd timer مقاوم به reboot، runner جدید را اجرا می‌کند. runner با flock فقط یک‌بار هم‌زمان وارد کانتینر API می‌شود. برنامهٔ `telegram-backup.cjs` از helper موجود `createEncryptedBackup` و اطلاعات ربات/ادمین محیط کانتینر استفاده می‌کند؛ کلید خصوصی age همچنان خارج از سرور است. فایل SQL خام ارسال یا روی میزبان ذخیره نمی‌شود.

فقط `.sql.gz.age` مجاز است. موفقیت نیازمند پاسخ Telegram با message id، سند با نام همان فایل و chat خصوصی با شناسهٔ دقیق ادمین است. حداکثر سه تلاش روی همان فایل رمز‌شده انجام می‌شود؛ پس از موفقیت یا شکست، فایل موقت داخل کانتینر پاک می‌شود. شکست با exit غیرصفر و پیام ثابت در journal دیده می‌شود؛ متن خطای provider، توکن و دادهٔ بانک چاپ نمی‌شوند. در قطع شبکه ممکن است Telegram پیام را بگیرد ولی پاسخ نرسد؛ تلاش مجدد می‌تواند یک نسخهٔ اضافی ارسال کند. ارسال دقیقاً یک‌باره تضمین نشده است.

زمان‌بندی: روزانه ۰۴:۱۵ Europe/Berlin با تأخیر تصادفی حداکثر ۱۵ دقیقه و Persistent=true. `BACKUP_INTERVAL_HOURS=0` باقی ماند تا scheduler داخلی ربات نسخهٔ دوم نفرستد. timer همان نام `oosta-backup.timer` و service همان timeout ۳۰۰ ثانیه را دارد. در شکست همهٔ تلاش‌ها، فایل موقت نگه داشته نمی‌شود؛ بکاپ‌های موفق قبلی در تلگرام/نسخهٔ محلی بازیابی باقی می‌مانند و خطای service باید بررسی شود.

کد اجرایی وب/API، DTO، validation و مجوز endpointها تغییر نکردند؛ runner از اعتبارنامهٔ سرور استفاده می‌کند و هیچ endpoint عمومی برای ایجاد یا بازیابی بکاپ باز نشد. سفارش، پرداخت، موجودی و تحویل تغییر نکردند.

## آزمون و عملیات

- تست قبل از پیاده‌سازی نبود برنامهٔ ارسال را بازتولید کرد. شش تست ساختگی اکنون ارسال رمز‌شده، مقصد ادمین، retry محدود، شکست دائم/پاک‌سازی، رد plaintext و مقصد متفاوت و رد شناسهٔ نامعتبر را بررسی می‌کنند. هیچ پیام واقعی در تست‌ها ارسال نمی‌شود.
- در اولین بررسی عملیاتی، Node هنگام خواندن از stdin شرط `require.main === module` را برقرار نکرد و برنامه اجرا نشد. assertion تأیید پیام جلوی گزارش موفقیت کاذب را گرفت. برای این حالت regression قرمز نوشته شد (exit صفر به‌جای یک)، ورودی stdin اصلاح و تست سبز شد.
- آزمون shell با docker ساختگی، stdin، انتقال خطای ارسال و قفل هم‌زمان را تأیید کرد.
- پس از درخواست صریح مالک، ارسال واقعی اجرا شد: `TELEGRAM_ENCRYPTED_BACKUP_SENT messageId=227`، service با `Result=success` و `ExecMainStatus=0`. این تنها فراخوانی واقعی Telegram در این مرحله بود و آزمون خودکار نبود.
- timer فعال/enable است و واحدهای systemd اعتبارسنجی شدند. شمار فایل‌های رمز‌شدهٔ موقت در کانتینر پس از ارسال صفر بود.
- فایل روزانهٔ قبلی `oosta-daily-20261117T105233Z.sql.gz.age` فقط بعد از تأیید ارسال جدید و تطبیق هش شناخته‌شده حذف شد. دایرکتوری daily خالی است. بکاپ‌های تاریخی قبل از انتشار که برای rollback نگه داشته شده بودند دست نخوردند؛ ادعای حذف تمام آرشیوهای قدیمی سرور نمی‌شود.
- آرشیوهای ارسالی برای بازیابی به کلید محلی `%LOCALAPPDATA%/OostaRecovery/backup-key.txt` نیاز دارند. کلید خصوصی ارسال یا در مخزن ثبت نشد. این بکاپ جدید decrypt/restore نشد؛ آزمون بازیابی ساختگی قبلی همچنان جداگانه مستند است.

بررسی وضعیت و اجرای دستی مجاز:

```bash
systemctl status oosta-backup.timer oosta-backup.service --no-pager
journalctl -u oosta-backup.service -n 20 --no-pager
systemctl start oosta-backup.service
```

## کنترل‌های انتشار

تست‌های ساختگی به `test:contracts` اضافه شدند. verify کامل و build production با exit صفر تمام شدند؛ lint کامل و lint مجدد فایل‌های جدید موفق بود. هر دو audit صفر آسیب‌پذیری گزارش کردند. تغییر وابستگی وجود ندارد. نتیجهٔ این کنترل‌ها تضمین بی‌باگ یا امن‌بودن همهٔ سیستم نیست.
