## ۱. ثبت بازدید که هرگز کار نکرده بود

- **مشکل:** کامپوننت `Track` در هر بازدید صفحه یک `POST /api/track` می‌فرستد. اما در nginx حالت پیش‌نمایش، بلوک `/api/` هر درخواست غیر از GET را 503 برمی‌گرداند.
  - در لاگ دسترسی، **۱۷۶ از ۱۷۶** درخواست 503 گرفته بودند.
  - برای همین جدول `visits` خالی بود و گزارش بازدید در ربات تلگرام چیزی نشان نمی‌داد.
- **وضعیت API:** سمت API از قبل امن بود:
  - user-agentهای ربات را کنار می‌گذارد.
  - فقط مسیر صفحه را نگه می‌دارد و مسیرهای ادمین را ثبت نمی‌کند.
  - به‌جای IP خام، یک hash روزانه از IP و user-agent ذخیره می‌کند.
  - رکوردهای قدیمی‌تر از ۹۰ روز را پاک می‌کند.
- **اصلاح:**
  - **`deploy/nginx/oosta-visit-tracking.conf`:** یک `location = /api/track` که فقط POST و OPTIONS را به `/track` می‌فرستد و درخواست‌های دیگر 405 می‌گیرند. حجم بدنه به ۲ کیلوبایت محدود است و `limit_req` با سقف ۶۰ درخواست در دقیقه و burst ۲۰ اعمال می‌شود.
  - **`deploy/nginx/oosta-track-limit.http.conf`:** روی سرور در `conf.d` نصب شد.
  - **کلید محدودیت نرخ:** nginx سرور IP واقعی کاربر را نمی‌بیند و `$remote_addr` آدرس لبهٔ آروان است. پس هدر `ar-real-ip` فقط وقتی پذیرفته می‌شود که اتصال از بازه‌های IP آروان بیاید. این بازه‌ها از `trusted-cdn.conf` کپی شدند. در غیر این صورت آدرس اتصال کلید است. `trusted-cdn.conf` را سراسری نصب نکردم، چون IP دیده‌شده در کل API را عوض می‌کرد.
- **رگرسیون:**
  - `preview-http-check --tracking-ready` چک می‌کند که POST به `/api/track` پاسخ 204 بگیرد و GET پاسخ 405.
  - `preview-http-regressions` حالت قبل از اصلاح (503) و بعد از آن را شبیه‌سازی می‌کند.
  - بررسی زنده قبل از اصلاح شکست خورد و بعد از آن پاس شد.
- **نصب:**
  - پیش از تغییر، از کانفیگ سایت backup گرفته شد (`oostaai.store.pre-visit-tracking-20261118`).
  - بعد `nginx -t` اجرا شد و nginx فقط reload شد.
  - اگر `nginx -t` شکست می‌خورد، backup خودکار برمی‌گشت و فایل `conf.d` حذف می‌شد.
- **بررسی سرتاسری:** یک بازدید واقعی از `/fa/blog` در مرورگر داخلی یک ردیف در `visits` ساخت، با `path=/fa/blog`، کد کشور و hash ۶۴ نویسه‌ای و بدون IP.
- **commit:** `a931596`
