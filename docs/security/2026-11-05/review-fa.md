# بررسی کیفیت، قرارداد API و امنیت — ۵ نوامبر ۲۰۲۶

این مرحله بهبود مسیر محصول، پرداخت و سفارش است. نتیجهٔ تست‌های محلی، تضمین نبود آسیب‌پذیری یا تأیید امنیت سرور منتشرشده نیست.

## اصلاحات انجام‌شده

| مورد | رفتار قبلی | رفتار جدید و شاهد |
|---|---|---|
| پول دریافت‌شده و موجودی تمام‌شده | API خطای 409 برمی‌گرداند؛ callback آن را «نتیجه نامشخص» نشان می‌داد، با وجود وضعیت قطعی پرداخت در DB | پاسخ `200 {status:"pending", orderId}`؛ callback به همان سفارش می‌رود و سفارش توضیح «نیازی به پرداخت دوباره نیست» دارد. آزمون رقابت دو پرداخت برای یک موجودی در smoke و آزمون رندر کامپوننت واقعی |
| سفارش کارت‌به‌کارت بازپرداخت‌شده یا بسته | فرانت برای هر وضعیت غیر PAID لینک تکمیل پرداخت داشت؛ DTO نیز اطلاعات کارت را برمی‌گرداند | فقط PENDING، PENDING_REVIEW و REJECTED اطلاعات/عمل پرداخت دارند. تست برای REFUNDED، EXPIRED، PAID_PENDING_FULFILLMENT و PAID؛ تست DTO واقعی سفارش بازپرداخت‌شده |
| پاسخ‌های خصوصی API | Cache-Control صریح نداشتند | `private, no-store` برای auth، orders، tickets، admin و payment verification. تست middleware واقعی |
| اختلال دیتابیس هنگام احراز هویت با API key | به 401 تبدیل می‌شد و می‌توانست به‌جای اختلال سرویس، کلید نامعتبر به کلاینت گزارش کند | خطای زیرساخت به error handler منتقل می‌شود؛ کلید واقعاً ناشناخته همچنان 401 است. تست خطای ساختگی DB |
| سرصفحه‌های امنیتی فرانت | محافظت frame در Next.js پیکربندی نشده بود | X-Frame-Options=DENY، nosniff، Referrer-Policy و CSP شامل frame-ancestors، base-uri و object-src. تست پیکربندی و پاسخ HTTP واقعی پیش‌نمایش |
| پیگیری سفارش | دریافت ناموفق سفارش فقط پیام عمومی داشت | استفاده از QueryError و تلاش دوباره؛ وضعیت منتظر تحویل با رنگ خنثی و مسیر پشتیبانی |

Schema و migration جدیدی برای این اصلاحات لازم نشد؛ وضعیت `PAID_PENDING_FULFILLMENT` از قبل در DB وجود داشت. منطق قیمت‌گذاری، درگاه واقعی و سطح دسترسی کاربران تغییر نکرد.

## بررسی‌های موفق

- `npm run verify`: TypeScript هر دو workspace، رندر واقعی OrderDetail با DTO ساختگی، تست‌های امنیتی و مجموعهٔ DB موقت.
- API smoke: هر **۱۵۲ بررسی** موفق؛ شامل دسترسی متقاطع سفارش/تیکت، نقش‌ها، اعتبارسنجی، قراردادهای کاتالوگ و پرداخت.
- Regression روی PostgreSQL موقت: تحویل هم‌زمان فقط یک واحد، لغو callback بدون از بین بردن پرداخت، رقابت رسیدها، عدم بازگشت موجودی افشاشده به فروش، سقف رسید، حفظ وضعیت پرداخت‌شدهٔ منتظر تحویل، بازیابی backup، و جلوگیری از ارتقای سطح با ادعای ADMIN قدیمی در JWT.
- تست امنیت: محافظ‌های production، چت خصوصی ربات، تأیید یک‌بارمصرف تغییر تنظیمات عامل، رد sandbox تولید، no-store، و تفکیک خطای DB از کلید نامعتبر. ارتباط Telegram/مدل‌ها جایگزین شد و پیامی ارسال نشد.
- `npm run build`: ساخت API و production build وب هر دو موفق؛ ۴۷ صفحه تولید شد.
- ESLint فایل‌های تغییرکرده موفق.
- HTTP محلی `/fa`: وضعیت 200 و سرصفحه‌های DENY، nosniff و CSP جدید مشاهده شد.

آزمون‌های DB با `scripts/test-isolated.cjs` در یک کلاستر جدا، migrationهای واقعی و دادهٔ ساختگی اجرا شدند؛ کلاستر در پایان متوقف و حذف شد. دیتابیس کاری، حساب مشتری و پرداخت واقعی استفاده نشد.

## موارد باز وابستگی‌ها

**npm audit هنوز پاک نیست.** نتیجهٔ کامل در `npm-audit.json` و نتیجهٔ `--omit=dev` در `npm-audit-production.json` همین پوشه ثبت شده است.

- اسکن بدون dev: **۳ high، صفر critical**. این سه ردیف یک زنجیره‌اند: `prisma@6.19.3 → @prisma/config@6.19.3 → deepmerge-ts@7.1.5`.
- اسکن کامل: **۳ high و ۸ moderate، صفر critical**. ردیف‌های moderate به زنجیرهٔ ابزارهای lint و `minimatch@10.2.6` مربوط‌اند؛ هشت نقص مستقل اثبات نشده است.
- deepmerge: ادغام دو آبجکت دارای ارجاع حلقوی، stack را تمام می‌کند. نسخهٔ اصلاح‌شده 8.0.0 است. JSON عادی به‌تنهایی حلقه ایجاد نمی‌کند. در مسیرهای HTTP بررسی‌شده، ورودی عمومی مستقیم به این ادغام تنظیمات پیدا نشد؛ این محدودیت بررسی است و یافته را منتفی نمی‌کند. [هشدار رسمی](https://github.com/advisories/GHSA-ggr8-5vv4-36mx)، [تغییرات major 8](https://github.com/RebeccaStevens/deepmerge-ts/releases/tag/v8.0.0).
- minimatch: الگوی glob کنترل‌شده توسط مهاجم، تحت optimizationLevel مناسب، می‌تواند مصرف CPU/حافظه را افزایش دهد؛ نسخهٔ اصلاح‌شده 11.0.1 است. مصرف‌کنندهٔ نصب‌شده در این پروژه ابزار توسعه است. [هشدار رسمی](https://github.com/advisories/GHSA-g3hv-75wg-m249).

آزمایش override و pin نسخهٔ جدید deepmerge روی این npm/workspace، شاخهٔ مورد استفادهٔ Prisma را به نسخهٔ اصلاح‌شده منتقل نکرد. آزمایش برگشت داده شد: dependency جدید، override یا تغییر lockfile از این تلاش باقی نماند. ارتقای ORM یا ابزارهای lint به major ناسازگار، بدون مرحلهٔ مهاجرت و تست جداگانه انجام نشد. `node scripts/audit-prisma-merge.cjs` بازتولید مستقل یافتهٔ باز است و اکنون عمداً با assertion شکست می‌خورد؛ جزو فرمان سبز verify نیست.

## روش ادامهٔ هر مرحله

1. قرارداد UI و API و مرز مجوز همان تغییر را بخوان؛ ایراد را با تست قرمز بازتولید کن.
2. اصلاح کوچک، تست‌های موفق/ناموفق و بررسی نشت داده و دوباره‌کاری مالی.
3. `npm run verify` و ESLint مرتبط؛ برای انتشار `npm run build` و هر دو audit را هم اجرا کن.
4. نتیجه و موارد باز را صریح گزارش کن. عبور verify به معنی بسته‌شدن هشدارهای audit نیست.

این روش در AGENTS.md ریشه هم ثبت شد.

## محدودیت‌های این مرحله

- پرداخت واقعی زرین‌پال، TLS/CDN/WAF، مجوزهای سرور و شرایط استقرار عمومی تست نشدند؛ فقط کد و تنظیمات نمونهٔ reverse proxy خوانده شد.
- این بررسی یک دور هدفمند از مسیر خرید، دسترسی و رندر خروجی است، نه اثبات رسمی همهٔ حالت‌های برنامه.
- دروازهٔ وابستگی‌ها هنوز برای ادعای «بدون هشدار امنیتی» عبور نکرده است. مرحلهٔ مهاجرت امن وابستگی‌های بالا باید جداگانه تکمیل شود.
