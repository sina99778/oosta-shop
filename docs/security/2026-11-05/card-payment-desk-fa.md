# بازطراحی میز پرداخت اوستا — ۵ نوامبر ۲۰۲۶

کاربر طرح «میز پرداخت اوستا» را تأیید کرد. صفحهٔ واقعی کارت‌به‌کارت با همان هویت سرمه‌ای/نعنایی بازطراحی شد: کارت مقصد با شمارهٔ LTR گروه‌بندی‌شده، مبلغ روشن، کپی با بازخورد، آپلود همراه با پیش‌نمایش و خلاصهٔ سفارش/رسیدها. فرمت مالی مشترک حفظ شد: ۴٬۹۹۰٬۰۰۰ ریال برای فارسی، ۴۹۹٬۰۰۰ تومان نمایش داده می‌شود.

## قرارداد و امنیت

- مسیر فرانت: `checkout/card/[orderId]` با RequireAuth → `GET /orders/:id` با Bearer → DTO `OrderDetail`؛ ارسال multipart به `POST /orders/:id/receipt` با همان فیلدهای receipt و reference. schema و migration جدیدی اضافه نشد.
- مالکیت در API با id سفارش و userId بررسی می‌شود؛ provider باید CARD_TO_CARD باشد. وضعیت‌های مجاز PENDING/PENDING_REVIEW/REJECTED و تراکنش/قفل و سقف ۵ رسید برای سفارش، ۲۰ رسید روزانهٔ کاربر تغییر نکردند. سقف فایل API همچنان ۵ MiB است.
- نسخهٔ قبلی هنگام PENDING_REVIEW باز هم مقصد و دستور واریز را نشان می‌داد؛ تست ابتدا روی همان نسخه قرمز شد. اکنون مقصد در این حالت نمایش داده نمی‌شود؛ وضعیت «دریافت رسید، منتظر بررسی» غالب است و ارسال رسید دیگر فقط با انتخاب صریح کاربر باز می‌شود. ارسال رسید، تأیید پرداخت معرفی نمی‌شود.
- PAID، PAID_PENDING_FULFILLMENT، REFUNDED و EXPIRED کارت و upload را حتی با DTO ساختگیِ دارای کارت پنهان می‌کنند. پرداخت تأییدشدهٔ منتظر تحویل صریحاً از پرداخت دوباره منع می‌کند. نبود اطلاعات کارت پیام راهنما دارد.
- نشانگر پیشرفت با تست قرمز جدا بررسی و اصلاح شد: پس از ارسال رسید، مرحلهٔ بررسی فعال است، نه ثبت رسید. انتخاب فایل پیش از ارسال فقط مرحلهٔ ثبت را نشان می‌دهد و تأیید مالی نیست.
- اعتبارسنجی انتخاب فایل بلافاصله فرمت، خالی‌بودن و سقف حجم را بررسی می‌کند. این کنترل UX جایگزین API نیست. پیش‌نمایش فقط raster محلی با blob URL است؛ PDF embed و SVG وجود ندارد. blob URL در replace/unmount آزاد می‌شود و file قدیمی نمایش داده نمی‌شود.
- هنگام ارسال، ورودی‌ها قفل و ارسال تکراری هم‌زمان با ref مسدود می‌شود؛ idempotency مالی همچنان مسئولیت API است. خطای upload فایل و reference را پاک نمی‌کند. token، receipt و شماره کارت وارد storage جدیدی نمی‌شوند. کپی به clipboard فقط با کلیک کاربر است؛ شکست/انتظار آن بازخورد دارد.
- پاسخ‌های خصوصی و مجوزهای DB/API در این تغییر دستکاری نشدند. production preview همچنان نوشتن، ثبت‌نام، سفارش و payment verification را در Nginx مسدود می‌کند؛ فروش واقعی فعال نشده است.

## بررسی‌های مشاهده‌شده

- `npm run verify`: موفق؛ تست‌های جدید کارت‌به‌کارت جزو `test:contracts` شدند. تست‌های API/امنیت و DB موقت، ۱۴ migration، ۱۵۲ smoke و regressionهای race، مالکیت/نقش، موجودی و restore موفق شدند. DB کاری reset/seed نشد.
- `npm run build`: API و وب موفق؛ ۴۷ صفحه تولید شد. ESLint فایل‌های کامپوننت، route، validator و harness/testها موفق شد.
- هر دو `npm audit` و `npm audit --omit=dev`: صفر هشدار شناخته‌شده در زمان این مرحله. dependency جدیدی اضافه نشد.
- تست SSR کامپوننت واقعی با DTO ساختگی: کارت در pending، پنهان‌سازی در review/closed، مبلغ ریال/تومان، مرحلهٔ بررسی و retry خطای fetch؛ فارسی و انگلیسی. تست validator: سقف حجم دقیق، حجم اضافه، فایل خالی، PDF و رد SVG.
- مرورگر با API ساختگی فقط روی loopback: ورود ساختگی، خطای انتخاب SVG، پیش‌نمایش PNG، بازخورد موفق کپی، خطای submit بدون فایل و ارسال شبیه‌سازی‌شده تا وضعیت review مشاهده شد. در عرض ۳۹۰px، عرض محتوا ۳۸۲px بود و overflow افقی مشاهده نشد. دسکتاپ ۱۳۶۰px و موبایل بازبینی شدند؛ screenshotهای محلی در پوشهٔ screenshots ثبت شده‌اند.
- بازبینی مستقل مسیر UI تا API، lifecycle فایل/clipboard، مجوز/سقف رسید و کنترل‌های دسترسی، ایراد قابل‌اقدامی پیدا نکرد. مرورگر و build کامل را مستقل تکرار نکرد.

## به‌روزرسانی سرور پیش‌نمایش

فقط پنج فایل فرانت (کامپوننت، validator، route و دو dictionary) به release جداگانهٔ `/opt/oostaAI/releases/20261105-card-desk` منتقل شدند. ساخت Docker وب روی لینوکس نیز موفق شد و فقط سرویس web با `--no-deps --no-build` تعویض شد. API و PostgreSQL زمان شروع قبلی را حفظ کردند؛ هر سه Oosta container دارای restart=0 و OOM=false بودند. شروع اولیهٔ وب یک پاسخ reset گذرا داشت؛ بررسی بعدی پس از آماده‌شدن، موفق شد.

لینک `/opt/oostaAI/current` پس از health موفق به release جدید اشاره کرد. image قبلی برای rollback فرانت با tag `oosta-web:before-card-desk-20261105` نگهداری شد. هیچ migration، secret یا داده‌ای در این انتشار تغییر نکرد. fixture طراحی و فایل‌های رسید ساختگی به سرور منتقل نشدند.

`node scripts/preview-http-check.cjs https://oostaai.store --login-ready` پس از تعویض وب موفق شد؛ صفحه و assetها 200، مجوزهای خصوصی و no-store، ورود HTTPS، مسدودبودن mutationها و نبود فایل env بررسی شدند. صفحهٔ واقعی کارت‌به‌کارت روی سرور همچنان به سفارش احرازشده نیاز دارد؛ برای نمایش طرح، سفارش آزمایشی در DB منتشرشده ساخته نشد. پیش‌نمایش تعاملی محلی در `http://127.0.0.1:3102/fa/checkout/card/desk-preview` با دادهٔ ساختگی آماده است.

## محدودیت‌ها

رسید، شماره کارت، حساب و سفارش استفاده‌شده در مرورگر ساختگی بودند. harness `scripts/card-checkout-preview.cjs` فقط روی 127.0.0.1:4402/3102 اجرا می‌شود، احراز هویت شبیه‌سازی‌شده دارد و نباید به اینترنت یا محیط واقعی متصل شود. این fixture تأیید صحت پرداخت یا سند بانکی نیست. تعامل drag/drop، خطای واقعی شبکه وسط upload و مرورگرهای مختلف مستقلاً تست سرتاسری نشده‌اند؛ شکست‌های API با مجموعهٔ جاری و بازبینی مسیر بررسی شدند. امنیت کامل محیط مستقر یا نبود باگ ادعا نمی‌شود.

حساب محلی fixture در `preview@example.invalid` با رمز ساختگی دلخواه پذیرفته می‌شود؛ این رفتار فقط در API fixture است و در سرور واقعی وجود ندارد. برای مشاهدهٔ طراحی، ساخت سفارش واقعی یا فعال‌کردن درگاه لازم نیست.
