# Oosta: private Blu deposit reconciliation

Status: design proposal; no bank connection, login, device enrollment or production activation performed.

## User intent and known decisions

Automatically confirm actual card-to-card deposits while the online gateway is inactive. Preserve approved navy/mint checkout and existing receipt/manual-review fallback. User owns a Blu account also used personally and has a private Iran server. Do not request bank passwords or OTP in chat. The user approved a unique, clearly displayed payable amount for each order and supplied Iran server address `85.133.162.92`. On 2026-11-11 ICMP responded, but SSH on TCP 22 timed out before authentication. Confirm the SSH port and username and, if port 22 is intended, check the provider firewall and sshd from the server console. Verify the host key fingerprint before the first login. No supplier purchase or public checkout is enabled as a side effect.

## Approach and security boundary

Use a minimal collector on the private Iran server, separate from the storefront VPS. Import only the protocol/client and minimal transaction decoder from reviewed upstream commit fa159bc53a8432f922b7c57572e3db9669e29520; do not run upstream server.js or expose its broad HTTP API. No transfer, card-OTP, raw-call, link creation, account changes, or generic remote bank-path API exists in our collector. The main shop never receives bank credentials, session keys, balances, profile/contact information or the personal full history.

Alternatives considered: running the full upstream server alongside the shop exposes unnecessary bank operations and couples compromises; an official bank-scoped read-only integration would provide a stronger credential boundary but is not supplied by this repo. Chosen proposal is isolated collection with strict data minimization. IMPORTANT: its underlying bank session still has broad bank permissions. Removing transfer endpoints is an application restriction, not a bank-issued read-only token. Process/host compromise can still compromise the account; encryption does not remove this risk.

Collector runs unprivileged, no Docker socket/host admin mounts, read-only code filesystem and a private writable state directory. Only outbound connections to the fixed bank hostname and fixed Oosta ingestion origin; no public listener. SSH access restricted. Credentials/session state encrypted at rest with an independent host secret outside source/images/backups; no secrets in arguments/logs. Bank-password retention for unattended renewal is an explicit secret-management requirement; a 15-minute token alone cannot promise continuous operation. Initial login/device OTP is performed interactively by the owner in the private server environment; do not weaken authentication or bypass a challenge.

Use a dedicated collector signing key (Ed25519, Node crypto); Oosta has only its public verification key. Collector polls fixed Oosta invoice manifest using a separate narrowly scoped credential, and pushes strictly typed signed candidate events. Payloads include account alias (not full PAN), provider transaction ID, integer IRR amount, currency, credit direction, final status, bank time, invoice correlation, schema/key version, signed sentAt and unique event ID. No customer-supplied URL or bank path is accepted. Reject invalid signature/body size/schema/account/currency/time/status. Persist replay keys and bank transaction identity; do not rely on in-memory replay state.

Because the account is personal too, filter locally against a minimal store watch set before pushing: active invoices, expired/closed allocations retained for late-money review, and claimed bank transaction IDs retained for duplicate/reversal observation. Do not fetch/push only active invoices and silently discard late money. Retain watched allocations for at least 90 days in the initial implementation; retain already claimed transaction identities and allocation non-reuse tombstones for the financial audit lifetime, without full personal statement bodies. The watch set must be replayable from durable state after restart; reverse-status changes to an already watched bank ID are review events, even after invoice expiry. This is bounded observation, not a guarantee of detecting a reversal that the bank never exposes. Retain only the cursor and minimal candidate evidence needed for reconciliation; no personal transaction dumps in shop logs or databases. Exact counterparty identity is not a prerequisite for a gift payment; do not pretend a typed tracking code proves payer identity.

## Matching and ownership

Approved choice: allocate a distinct clearly displayed payable amount per open invoice, with the adjustment shown before commitment. Price accounting must record base price, adjustment and exact amount separately and normalize IRR/IRT only once using integer arithmetic. The candidate allocator must avoid cross-base-price collisions, serialize allocation, and never silently reuse an old amount while late deposits can be auto-matched. MVP conservative rule: retain old allocations; an expired allocation is never silently reassigned for automatic confirmation. Exhausted space fails to manual review, not an overlapping invoice.

If the user keeps exact list price, amount/time alone is insufficient when invoices collide. Require bank reference and available independent matching evidence; multiple plausible invoices stay manual. A unique amount alone also does not prove an unrelated personal credit belongs to the order. Shared-account auto-confirmation therefore remains gated on independently demonstrated bank correlation (not just amount) and an explicit final rollout decision acknowledging residual attribution risk. Prefer a separate receiving account/card used exclusively for the shop; a business profile sharing the same bank login helps attribution but does not reduce the full-session credential risk. Shadow mode can be implemented and tested with the current shared account. Neither a receipt picture, OCR result nor typed reference is proof of a credit. Even with a unique amount, verify actual successful CREDIT into the configured receiving account, exact currency/amount and invoice window. A transaction can satisfy at most one order. A screenshot and transaction reference remain optional assistive data; avoid requiring an image for an already proven deposit.

The order stores an immutable receiving-account/amount/currency/time-window snapshot. Bank config changes never rebind existing invoices. Owner-only checkout/status endpoints, current database admin roles for settings/manual decisions, private no-store responses. Do not reveal to one customer whether a different customer's reference exists. Account mismatch, failed/pending/reversed/debit, ambiguous direction, unknown enum/field or malformed timestamp -> manual review/hold, never payment success.

## Durable financial evidence and fulfillment

Current manual approveReceipt calls deliverOrderInTransaction in the same transaction as receipt approval. That helper treats PAID as already fulfilled and rolls back when inventory is unavailable. Do not merely call that function with a bank event and lose or reuse the real deposit after a delivery failure.

Add a minimal persistent bank-observation/claim ledger separate from receipt images. Unique provider+receivingAccount+transactionId; unique claim/order binding as appropriate. Commit authenticated bank evidence before attempting fulfillment. Claim allocation and order validation are serialized in database transactions and reconciled with manual approvals/cancellation. Preserve late money even for expired/refunded/closed orders, but route it to manual review rather than reopening them. If already manually paid, record evidence and avoid second delivery; do not consume a different transfer silently.

Maintain distinct observed/claimed/payment-confirmed and fulfillment states. The implementation must not set PAID first and then use the existing PAID-early-return helper expecting stock delivery. Either minimally refactor payment confirmation/fulfillment into explicit idempotent steps or use durable claim+retry state around the existing atomic delivery helper with an honest buyer status 'deposit confirmed, awaiting fulfillment'. Out-of-stock never erases bank evidence; retries never request another deposit. Supplier plans remain disabled by their existing sales guard.

Poll bounded recent pages with overlap/cursor, collect detail only for candidates, handle delayed/out-of-order entries and resume after restart. Never invoke upstream findTransaction's full-history scan for every visitor request. Upstream derive.transactionDetail currently renders localized display strings. Before real auto-confirmation, create and validate a field-mapping document from raw protocol evidence for stable transaction identity, exact receiving account, integer amount/currency, CREDIT and final-success semantics plus bank timestamp/timezone. Formatted labels are display-only. If the bank API does not expose enough authoritative evidence, retain shadow/manual mode instead of guessing finality. No promise of automatic matching feasibility precedes this gate.

Fixed retry/backoff and one worker/DB lease prevent banking traffic multiplication. On network/session/protocol failure, show 'awaiting verification' and retain manual review; never infer success from absence or a balance difference. A confirmed later bank reversal is a review event, not automatic stock reuse or disappearance of the ledger.

## Rollout and evidence

1. RED/GREEN synthetic parser, signed ingestion, authorization/ownership, duplicate/reordered events, replay/tampering, integer currency, unique amount collision/exhaustion, wrong account and all fail-closed paths.
2. Disposable DB tests only: concurrent claims/manual approval/cancellation/refund, missing stock, late deposits, restart/restore and one-delivery invariant. No live bank/model/notification calls in automated tests.
3. Full npm verify, affected/full lint, API/web production builds and both audits; independent design/code review; record actual results and limits in docs/security.
4. Back up working ledger; deploy collector with no bank session and shop feature disabled. Configure network/secrets privately. Owner enrolls own bank device interactively; never paste credentials/OTP into chat.
5. Read-only shadow collection for one explicit internal QA invoice/account allowlist: inspect typed real credit fields and false-positive filtering without marking paid.
6. Owner manually transfers a small explicitly agreed amount from another owned account to the configured receiving account. No API-generated outgoing transfer. Verify bank evidence, site status, ownership/cache, one delivery, event replay/restart and preserved ledger. The existing USD supplier-test budget is not permission for this separate IRR transfer.
7. Enable automatic confirmation gradually only after real trace passes; keep kill switch, manual fallback and minimum data retention policy. Broader public checkout activation is separately scoped, not an automatic consequence of installing this component.

No claim of guaranteed zero bugs, bank endorsement, immutable upstream protocol or genuine read-only bank permissions is made. Upstream is public source; check its applicable license before copying code into the commercial deployment, as no standalone license was seen during the initial review.


## Independent builder review and resolved gates

Reviewer identified shared-account false attribution, active-only loss of late/reversed events, and unproven raw final-credit decoding. The proposal now explicitly gates live automation, retains a minimal historical watch set and requires verified raw field semantics. Review also confirmed the existing PAID/fulfillment coupling must be handled explicitly. The approved amount choice allows synthetic implementation with the feature disabled; actual automatic bank confirmation is conditional on those evidence gates. Restore must pause auto-confirmation via operational state outside the restored DB, then reconcile the collector event journal and current bank evidence before resuming; old backup restoration must never reset duplicate protection and recycle a deposit.
